# Chat channels

Lost Tales provides five player-conversation channels while leaving commands, server messages, death messages, and other mods' chat components on Minecraft's normal paths.

Channels are presented — tabs, the `[Channel]` indicator, and `TAB` cycling — in this order:

- **Global** (channel id `all`) is global in-character conversation.
- **Proximity** is in-character conversation delivered only to players in the sender's dimension and within the server's configured radius.
- **Faction** is in-character conversation delivered only to online characters whose configured faction matches the sender's active character. It is unavailable without a valid active-character faction.
- **OOC** is global out-of-character conversation and uses the Minecraft account name and account skin.
- **Party** is in-character conversation delivered only to online members of the sender's current Lost Tales party. It is unavailable without a valid party.

The presentation order is `ChatChannel.presentationOrder()`; the enum's declaration order is left alone because client view state is indexed by ordinal, and channel ids on the wire are strings.

In-character messages require an active role-playing character and snapshot its name and skin when the server accepts the message, so existing history does not change after a character switch. The current LOTR title and the exact color exposed by LOTR's faction explorer are snapshotted presentation details. Players without an active character can use OOC with their account identity and skin, but cannot send to Global or another in-character channel.

LOTR NPC speech that would print as a plain yellow chat line is restyled on the client into the same presentation: an NPC message shows the Proximity channel when the NPC is within the server's proximity radius (Global otherwise), a timestamp, the NPC's rendered skin as its head icon, and a honey-coloured name. This is purely visual — a coremod hook replaces only the final chat print in LOTR's speech packet handler, so speech content, recipients, NPC behaviour, and LOTR's immersive floating speech are untouched, and any failure falls back to LOTR's original line. It can be disabled with `client.enableNpcChatStyling`.

Chat lines are spaced eleven pixels apart (vanilla uses nine), each line's backdrop filling the full stride so neighbouring bands connect seamlessly; the extra height is what gives inline emotes and head icons their room. Channel colours come from the shared palette — Global is meadow green, Proximity teal, Party seafoam, OOC orchid — except Faction, which shows the sender's exact LOTR faction colour; the `:` after the channel name and the channel indicator share the channel's colour, and timestamps use the palette's sand (`#dbc9b4`) in italics. Clicking a message's head icon fills the input with the same `/msg AccountName ` reply as clicking the name.

Players can style their own messages with `&`-formatting codes (`&6gold`, `&lbold`, `&r` reset — the usual Minecraft codes with `&` in place of the untypable section sign). Translation happens on the receiving client at display time; the wire format, copied text, and history keep the ampersand form. Mentioning someone with `@Name` — their account name or active character name, case-insensitive with word boundaries — highlights the message's backdrop in the palette's wine for the mentioned player and plays a ping sound on arrival (`client.chatPingSound`, the note-block pling `note.pling` by default; self-pings work). The cue is played as a non-positional UI sound on the mentioned client only: the server never triggers it and no other client hears it. Config files written by the first backport still carried LOTR's horn (`lotr:item.horn`) as the value; that legacy value is migrated back to the pling on load.

A message longer than the chat width wraps under its own body rather than back to the left edge:

```text
[12:34] <Aragorn> This is a long roleplaying message that
                  continues here instead of returning
                  to the far left side.
```

The layout is a proper model, not a post-hoc offset. Every Lost Tales line carries a zero-width body marker between its rendered prefix (channel, timestamp, brackets, head, title, name) and the message body; the coremod hooks the seam inside `GuiNewChat.func_146237_a` where vanilla has finished wrapping and is about to file lines into the history, and `ChatLineWrapper` lays the message out instead: it measures the prefix with the same formatting-aware width the renderer draws with (so `&`-codes cost nothing), breaks the body at spaces (dropping the break space, carrying active formatting codes onto the next piece, treating emotes and showcase icons as atomic words, and cutting a word longer than a whole line so any input makes progress), and opens each continuation line with an indent marker recording the prefix width twice — with the channel prefix shown (closed HUD) and hidden (open screen) — so lines sit under the body in both states. The renderer and every hit test advance the cursor by that marker, so clicks, hovers and the copy action on a wrapped line land where the line is drawn. Vanilla keeps the history, scroll, trimming and resize bookkeeping, and re-runs the layout from the original message whenever the chat width or GUI scale changes. A prefix so long it would leave no real room starts the body a line down with the indent capped at half the width; a prefix wider than the chat falls back to vanilla's wrapping. Without the coremod patch the markers are inert and lines wrap as vanilla wraps them. Typing `@` shows a completion list of online players (yourself first, then alphabetical), filtered live and accepted by click, Up/Down, Tab, or Enter, exactly like the emote completions. Each online player appears once: in OOC the list shows and inserts the Minecraft account name, in role-play channels the active character name, but typing either name finds the player (`@Steve` and `@Aragorn` both offer `Steve123` in OOC and `Aragorn` in Global). The pairing of account and character comes from the public appearance sync the server already sends for every online player (it now carries the account name), so the list never guesses from display names. Mention detection is purely client-side presentation (each client checks its own names), and `client.enableChatPings` turns the whole feature off.

With the chat screen open a message reads `[HH:mm] <HEAD Title CharacterName> Message`; with it closed the HUD shows every channel in one feed and prefixes each line with its channel, `Global: [HH:mm] <HEAD Title CharacterName> Message`. The prefix is built once and skipped at draw time while the tabs already separate channels. Channel names use normal title casing, and Faction uses the active faction's exact color. The invisible head marker reserves exactly the icon width; there is no extra visible padding inside the brackets, and both brackets use the character name's exact RGB color. Clicking the displayed name fills the chat input with `/msg AccountName `, including for character channels where the visible role-play name differs from the Minecraft account name. While chat is open, hovering the rendered head or name shows a bounded player card. Its first line is `Character Name (Account Name)` for a character identity and just `Account Name` for an account identity (OOC lines, players without a character) — never empty parentheses. Below it, each of race, faction (the character's selected starting faction, never alignment or reputation), level, gender, age, and the biography is shown only when known, the biography wrapped to the card and bounded to a few lines. The details come from the public active-character appearance the server synchronizes for every online player — the appearance sync now carries starting faction, level, age, and description alongside name, race, gender, skin and capes, all appended after the original wire layout — and are shown only when they describe the character the line names, so a historic line never borrows a later character's details.

While the chat screen is open, a row of folder-style tabs stands on top of the topmost visible message (on the baseline when the view is empty), riding along with the stack as messages arrive and as the history enters — one per channel currently available to the player. The selected tab comes forward, lifts slightly, and runs into the box; the others sit recessed behind their neighbours. Clicking a tab selects it; with an empty input, `TAB` (or clicking the `[Channel]` indicator beside the input) cycles available channels. With text or a command present, Minecraft's normal autocomplete remains active. The selected channel decides both which history is shown and where a new message is sent: each tab shows only its own channel's messages; vanilla lines such as achievements, command output, and other mods' messages appear in the Global tab only and keeps its own scroll position, which survives closing and reopening the screen. The history, its backdrop and the tabs are one motion group: opening the screen brings them in with the same sampler, easing, direction and duration every other Lost Tales screen uses (`client.guiAnimation*`), the tabs taking their position from the bands the history drew and their opacity and horizontal motion from the same sample, so they enter, settle and fade together. Only the input bar — with its indicator, toolbar buttons and popups — keeps its own entrance from the bottom. A tab that received messages while another tab was selected shows textual counters after its name: `Gondor (2) (5)`, where the first, salmon-coloured `(p)` is the number of unread messages that mentioned you and the second, honey-coloured `(x)` the number of other unread messages; a message is counted once, as a ping or as unread, never both. A counter appears only while its count is positive (`Party (3)` with no pings), caps at `(99+)`, updates as messages arrive, and clears once the tab is viewed. The counts live in `ClientChatChannelViews`, the single source of unread state. With the chat screen closed, the HUD overlay still shows the combined feed, so nothing is missed. Messages are never copied; the views are filtered indexes over vanilla's own history. Without an active character the Global tab stays readable (achievements and other vanilla lines live there) but only OOC accepts messages — the indicator shows a read-only channel muted and Enter shows a notice instead of sending; Party and Faction are omitted when the active character cannot use them. The tab row only appears once the open view has at least one line; Tab and the indicator still switch channels before that. Hovering a row of the mention completion list shows the same player card as hovering a name in chat. The Faction tab, indicator, and message prefix show the active character's LOTR faction name (for example `Gondor`) rather than the word "Faction"; the logical channel and its routing are unchanged, and the catalogue name is used if LOTR cannot resolve the faction. Right-clicking a visible message copies only its message body and briefly confirms the action. Chat and the other Minecraft GUI screens use the same Lost Tales cursor as the LOTR map.

Every overlay the screen draws — tabs, the channel indicator, the emote, item, marker and quest buttons, the completion lists, the pickers — registers the rectangle it actually painted for that frame (in screen space, whichever motion group drew it), and hover, tooltip, and click handling check that record before touching the message stack. While the pointer is inside an overlay, the lines underneath are neither hovered nor clickable, so no hover card, item tooltip, or link click can fire through a popup; because the record comes from the draw itself, visual and interaction order cannot disagree. Chat lines are hit-tested the same way: the HUD pass records the exact screen band of every line it draws (scroll, chat scale, view filtering, and entry motion included), and the hover card, component tooltips, clicks, and right-click copy resolve against those bands.

`chat.proximityRadius` is a server-authoritative gameplay setting. Timestamp visibility, the emote toggle, and the message, input-bar, and selector animation settings are client presentation preferences under the `client` category. A new message eases upward and slides in from the left with a short fade, briefly overshooting its resting position to the right before settling; the input bar and the history enter together with the same restrained overshoot. Vanilla's chat hit test (`GuiNewChat.func_146236_a`) is routed through the drawn bands by the coremod while the Lost Tales chat screen is open, so LOTR's achievement hover card and any other mod asking vanilla where the pointer is get the same answer as Lost Tales itself, and get nothing under a popup. Disabling animation does not alter layout, routing, history, or command behavior. Chat surfaces — the message backdrop and the input bar included — use the palette's plum black (`#2d1e2f`) at half opacity; the message backdrop fades to transparent over its final third, while the input bar is solid across its width.

## Emotes

Player channel messages may contain emote shortcodes such as `:smile:`. They travel as ordinary message text — the server, the packets, and copied messages always carry the canonical `:name:` form — and each receiving client with `client.enableChatEmojis` enabled renders recognized shortcodes as inline 10×10 sprites that participate in normal layout and line wrapping. Unknown, incomplete, or malformed values (`:does_not_exist:`, `:sm`, a lone `:`) stay literal text, so mixed setups degrade to readable shortcodes. Disabling the toggle also shows shortcodes as plain text.

A small smiley button at the right end of the chat input toggles the emote picker; selecting an emote inserts its shortcode at the current cursor position without disturbing the rest of the input, and the panel stays open for further picks. The picker has a search field that filters by name, a Favorites row (right-click any cell to toggle a favorite, marked with a small gold dot), a Frequently Used row ranked by how often each emote has been sent, and the full grid; hovering a cell shows its shortcode as a tooltip. Favorites and usage counts are per-installation client preferences stored in `config/losttales/chat_emotes.txt` — nothing is synchronized. The button and panels are positioned from the live chat geometry, so GUI scale and resolution changes are handled.

Typing an unclosed shortcode such as `:fl` shows a completion list above the input, filtered live as more characters are typed. Click a row or use Up/Down plus Tab or Enter to complete it (Enter never sends the message while the list is open); Escape hides the list without closing chat. Completions never anchor on the closing colon of an already-completed emote, and commands never trigger the list.

The canonical registry is the `ChatEmoji` enum (`chat/emoji/`), which doubles as the picker order. Adding an emote means drawing it into a free 10×10 cell of `textures/gui/emotes.png` (11-pixel stride, 1-pixel gutters) and adding one enum constant naming that cell; `ChatEmojiSheetTest` fails the build if the sheet and registry disagree. Shortcodes are lowercase `a–z`, `0–9`, `_` and are wire format: never rename or reuse one. `ChatEmoji` and the parser are deliberately free of client classes; sprites, markers, the picker, and rendering live in client-only code.

Every chat element shares one shadow rule: text, emotes, head icons, item icons and marker glyphs draw a flat `#2d1e2f` silhouette at half the content's opacity, offset one pixel down-right under it. Sprites get that through `LostTalesSilhouetteRenderState`, which swaps the texture environment so a textured quad takes its colour from one constant and only its alpha from the texture; a tinted copy of the sprite would keep its own dark outline and go black instead.

Inline glyphs — emotes, item icons, map-marker glyphs, and the quest glyph on the toolbar — follow one set of rules in `ChatInlineIcons`, in the message lines, the pickers, the completion lists and the toolbar buttons alike: a glyph occupies the ten-pixel slot its two bold spaces reserve and fills a ten-pixel content box centred in it, two rows above the text's top edge so it is centred in the eleven-pixel band. An emote is drawn 1:1, an item's sixteen-pixel sprite is scaled onto the box, and a marker's opaque artwork (using the art bounds the marker atlas already records, not its padded seventeen-pixel cell) is fitted into it by its larger edge, so every kind reads at the same apparent size with the same baseline, spacing and shadow. Marker glyphs are drawn in the chat's ivory foreground rather than their map colour, so they read as part of the line; the bracketed marker name beside one keeps the marker colour.

## Sharing items and locations

A player can share an item from their own inventory or a map marker inline. The toolbar beside the input runs, right to left: the emote button, the sword button, which opens an item picker (search field plus collapsible Hotbar, Inventory and Armour sections), the marker button, which opens a picker of every map marker the map would show, and the quest button. The marker picker opens with a **Favourites** section (right-click a row to toggle, marked with the same gold dot as the emote picker) and a **Recently Travelled To** section (the last eight destinations the player confirmed fast travel to on the map, most recent first), followed by one collapsible section per marker type — the glyph the marker is drawn with, which is the taxonomy the marker atlas already defines: Settlements, Graveyards, Forests, Mountains, Ports, Harbours, Bridges, Camps, Waypoints, Points of Interest, Quests and so on — instead of one generic "Point of Interest" list. Sections with nothing in them are not shown, and a search shows one flat result list. Favourites and recent destinations are per-installation client preferences stored in `config/losttales/map_markers.txt`, keyed by marker id; an id that names no visible marker on the current server is kept but not shown. The quest button opens the quest picker on the same frame; quest entries are not shareable yet, so it shows an empty-state line, and quest entries will slot into that picker without another redesign. Typing `[i:` or `[m:` instead shows a completion list (icons and names; duplicates are numbered `Name (2)`). Either inserts a token such as `[i:Iron Sword]`, `[i:Iron Sword#2]` for the second stack of that name, or `[m:Northgate Test City]`. A shared marker renders as its glyph in the chat's ivory plus its name in the marker colour; hovering shows its coordinates and clicking opens the LOTR map and flies the camera to it (with the selection frame when the marker is known locally). Up to three items fit in one message, and a token counts as a single character against the 100-character limit; pressing Enter on a message that is still too long keeps the text and shows the count instead of sending. When the message is sent, the client resolves each token to a reference — a slot index for an item, a marker id for a marker — and sends only that alongside the text; the server re-reads the slot from the sender's live inventory or the marker record from world data under the sender's own visibility rules, checks that the real name matches the token, and attaches a validated payload (a stack bounded to 1 KiB of compressed NBT, or the marker's public id, name, icon, colour, dimension and coordinates) to the message it distributes. Recipients render a validated token as a small icon plus the bracketed name in its rarity colour, with the item's normal tooltip (name, enchantments, lore, attributes, durability, mod tooltip lines) on hover; the stack is decoded once on arrival. A token the server could not verify — the item was moved or dropped before sending, the name no longer matches, a forged slot, or an over-sized stack — is delivered as the literal text the sender typed, and the sender is told once per message. Showcase tokens, like emotes, are plain message text on the wire and in copied history.
