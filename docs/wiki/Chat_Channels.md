# Chat channels

Lost Tales provides five player-conversation channels, a staff channel and a private console, while leaving commands, server messages, and other mods' chat components on Minecraft's normal paths; it only decides which tab such a line is filed under.

Channels are presented — tabs, the `[Channel]` indicator, and `TAB` cycling — in this order:

- **Global** (channel id `all`) is global in-character conversation.
- **Proximity** is in-character conversation delivered only to players in the sender's dimension and within the server's configured radius.
- **Faction** is in-character conversation delivered only to online characters whose configured faction matches the sender's active character. It is unavailable without a valid active-character faction.
- **OOC** is global out-of-character conversation and uses the Minecraft account name and account skin.
- **Party** is in-character conversation delivered only to online members of the sender's current Lost Tales party. It is unavailable without a valid party.
- **Operator** (channel id `admin`) is a staff channel: only server operators (permission level 2) can read it or talk in it, with their account identity. The tab appears only once the server has told the client the player is an operator (`LostTalesChatAccessPacket`, sent on login and whenever a staff message is refused), and the server checks operator status again on every send, so a client cannot claim the tab for itself.
- **Whispers** are private conversations between two accounts. `/msg`, `/tell` or `/w <player> [message]` — or clicking a sender's name or head in any line — opens a tab named after that player in the window you are typing in and selects it; text after the name is sent straight away. A whisper tab works like any other tab (drag, dock, detach, mute, close) and shows the sender's account identity; the first message from someone opens their tab on your side too, with a ping — unless the conversation is hidden (cog menu), in which case it stays closed and only counts unread. The server delivers a whisper only to the sender and that one online player, each told who the other party is, and refuses an unknown name with a notice; closing a whisper tab just hides the conversation until the next message. Conversations end with the session: whisper and NPC tabs are closed when the history goes (leaving a server) and are never written to the layout file. LOTR NPC speech (`LOTRSpeech.sendSpeech` goes to one player) appears as a whisper from the NPC, in a tab bearing its name and kept apart from a player of the same name (`npc:Name`); replying there sends nothing — nobody is on the other end — but the line is shown as a whisper of yours, for the fun of it. It is the one line the client signs itself, and it is signed the way the server would sign it (`ClientChatIdentity`): the appearance the tab currently speaks as, an account line carrying the roles the server stated on login and the colour they give it, a character line its own faction's colour and skin. Only the LOTR title is missing, being the server's to resolve. Hovering an NPC's head or name shows the same bounded card a player's does — the portrait, the name in its faction's colour, and the faction its speech was captured with — so an NPC reads as a player that happens not to exist.
- **Console** is the player's private console: what only this player sees — command output, fast-travel countdowns and timers, game-mode confirmations, whispers, LOTR notices, other mods' lines — lands in this tab only, keeping the conversation tabs clean. It takes commands only: plain text typed with the console selected is refused with a notice instead of being sent. It is always available and needs no character. Lines the whole server sees — vanilla and Middle-earth achievements, death messages, joins and leaves, `/say` and `/me` — are filed under **Global** instead, because they are conversation everyone shares.

Where a vanilla or LOTR line goes is decided by `ChatSystemLineClassifier` from the translation key the server built the component with (`chat.type.achievement`, LOTR's `chat.lotr.achievement`, `death.*`, `multiplayer.player.joined`, `chat.type.announcement`, …), never from its rendered text, so it does not depend on the client's language. Every incoming line is printed from the `ClientChatReceivedEvent` handler (at the lowest priority, after every other mod has seen the event) with a tracked line id, its channel prefix and a timestamp — `Console: [18:45] Your game mode has been updated`, `Global: [18:45] Player has just earned …` — so the feed names the channel and the tabs file it like any other line; the server's component itself is untouched. Adding a category means adding a key to the classifier, nowhere else. Lines printed directly on the client without passing through the event (a HUD toggle notice) stay untracked and show in the console without a prefix.

The presentation order is `ChatChannel.presentationOrder()`; the enum's declaration order is left alone because client view state is indexed by ordinal, and channel ids on the wire are strings.

In-character messages require an active role-playing character and snapshot its name and skin when the server accepts the message, so existing history does not change after a character switch. The current LOTR title and the exact color exposed by LOTR's faction explorer are snapshotted presentation details. Players without an active character can use OOC with their account identity and skin, but cannot send to Global or another in-character channel.

LOTR NPC speech that would print as a plain yellow chat line is restyled on the client into the same presentation: LOTR sends speech to one player, so an NPC message is a whisper from the NPC — a tab named after it — with a timestamp, the NPC's rendered skin as its head icon, and its name in the NPC's own faction colour — the same colour player lines wear — a factionless wanderer (LOTR's UNALIGNED, whose own colour is pure black) speaks in the palette's light rose grey, and an NPC whose faction cannot be read at all keeps LOTR's yellow-name honey. The conversation's tab and prefix take the same colour. LOTR's **immersive floating speech** — the words above an NPC's head after a right-click — reaches the conversation too: a second coremod hook, inserted directly after LOTR shows the floating text, files the same words into the NPC's tab, so talking to an NPC reads back like a direct message even while LOTR's own chat log is off; when the chat log *is* on, the same packet's chat print is recognised as already delivered and never doubles the line. This is purely visual — the hooks replace only the final chat print and add one call after the floating speech, so speech content, recipients, NPC behaviour, and the floating speech itself are untouched, and any failure of the chat print falls back to LOTR's original line while a failure of the immersive copy simply adds nothing. Both can be disabled with `client.enableNpcChatStyling`.

Chat lines are spaced eleven pixels apart (vanilla uses nine), each line's backdrop filling the full stride so neighbouring bands connect seamlessly; the extra height is what gives inline emojis and head icons their room. Channel colours come from the shared palette — Global is fern green, Proximity meadow green, OOC rose beige, Discord steel blue (`#577F9D`), Operator crimson, the Console mauve (`#7B6268`) — except Faction, which shows the sender's exact LOTR faction colour, and Party, which shows the colour the player wears in their party (seafoam outside one); the `:` after the channel name and the channel indicator share the channel's colour, and timestamps use the palette's rose beige (`#c3a79c`) in italics, a quiet grey a step below the sand body text. Clicking a message's head icon opens a whisper with the sender, exactly as clicking the name does.

Players can style their own messages with `&`-formatting codes (`&6gold`, `&lbold`, `&r` reset — the usual Minecraft codes with `&` in place of the untypable section sign). Translation happens on the receiving client at display time; the wire format, copied text, and history keep the ampersand form. Mentioning someone with `@Name` — their account name or active character name, case-insensitive with word boundaries — highlights the message's backdrop in the palette's dark mulberry (`#4e2b45`) for the mentioned player and plays a ping sound on arrival (`client.chatPingSound`, the mod's own bundled chime `losttales:chat.ping` by default; self-pings work). The cue is played as a non-positional UI sound on the mentioned client only — the server never triggers it and no other client hears it — and each play varies slightly in pitch (which is also its speed) and volume, the small humanization repeated one-shots usually get, so a burst of mentions does not stamp the identical sample out again and again. The names that reach a player are the same in every channel: the account and every character of their roster, so whoever they are speaking as, all their other names are aliases that still reach them — in the NPC conversations exactly as everywhere else. Config files written by earlier builds still carrying LOTR's horn (`lotr:item.horn`) or the note pling (`note.pling`) are migrated to the bundled chime on load.

A message longer than the chat width wraps under its sender rather than back to the left edge:

```text
[12:34] <Aragorn> This is a long roleplaying message that
        continues here under the opening bracket instead
        of returning to the far left side.
```

The layout is a proper model, not a post-hoc offset. A sender's name is the whole of it: the brackets answer to a hover and a click exactly as the name does, so the player card comes up wherever the pointer is over them, and the head keeps two clear pixels on each side — a slot the marker declares rather than spells out in spaces, since a space is four pixels and a bold one five and nothing between them is reachable. Every Lost Tales line carries a zero-width anchor marker after its header (channel prefix and timestamp), in front of the sender's opening bracket; each header run says which state it belongs to: the closed feed shows the channel prefix inline, and the timestamp never takes inline width at all — with the screen open it is drawn in a dedicated timestamp column at the window's left edge (below), and the feed does not show it — where only the first line of each minute carries it, since the clock has no seconds and a burst inside one minute would otherwise repeat the same `[HH:mm]` down the whole column — so neither state reserves width for something it does not draw; the coremod hooks the seam inside `GuiNewChat.func_146237_a` where vanilla has finished wrapping and is about to file lines into the history, and `ChatLineWrapper` lays the message out instead: it measures the header with the same formatting-aware width the renderer draws with (so `&`-codes cost nothing), breaks the text at spaces (dropping the break space, carrying active formatting codes onto the next piece, treating the head, emojis and showcase icons as atomic words, and cutting a word longer than a whole line so any input makes progress), stops the text at 95% of the window's width, leaving the rest as clear margin, and opens each continuation line with an indent marker recording both states' offsets: the open screen's continuation lines start at the message origin under the bracket, while the closed feed's start at the **left edge** with the whole width — the feed is a glance, and a full-width continuation reads better there than an indent aligning with a prefix several lines up. The renderer and every hit test advance the cursor by that marker, so clicks, hovers and the copy action on a wrapped line land where the line is drawn. Vanilla keeps the history, scroll, trimming and resize bookkeeping, and re-runs the layout from the original message whenever the chat width or GUI scale changes. A header so long it would leave no real room starts the text a line down with the indent capped at half the width; a header wider than the chat falls back to vanilla's wrapping. Without the coremod patch the markers are inert and lines wrap as vanilla wraps them. With timestamps on, every open window carries a **timestamp column** at its left edge, laid out from one shared definition (`ChatTimestampColumn`): window edge, three pixels, the timestamp (a column sized for the widest `[HH:mm]` the font can produce, so it never changes width as the clock turns), three pixels, a one-pixel ivory separator — strongest at its vertical centre, fading toward both ends, spanning the history between the rules — and three more pixels before the message content; the column band behind the timestamps is the panel's plum black at half opacity again, so they read as a margin. Each message is stamped once, on its first line, riding the stack's scroll and fade, and drawn over the line's own band — a mention's dark-mulberry tint above all — so the digits on a highlighted line read at the same brightness as every other timestamp instead of being darkened under the tint. With timestamps off none of that exists and message content begins three pixels from the window's edge; the renderer, the per-window wrapping and every hit test read the same offsets, so hover, clicks, wrapping and resizing stay aligned in both states. Text the chat did not compose itself — an achievement from vanilla (green, or purple for a special one), one from LOTR (yellow), any other mod's notice, a player's own `&`-codes — keeps the colour it asked for but is drawn in the palette's nearest tone, so the whole chat reads in one set of sixteen colours. Minecraft's "chat colours" option is honoured: switched off, every formatting code — the channel and name colours as much as a sender's `&`-codes — is stripped before measuring and drawing and the whole line is plain ivory, exactly as vanilla renders colourless chat; the layout measures the same stripped text so wrapping and drawing always agree. A mention's colour re-resolves as it is drawn: a line built moments before this client learned the roles behind a name — the access roster, or the holder's first line — catches up from the shared honey to the role's colour instead of keeping the fallback forever.

Enter sends the message and keeps the screen open with an empty field for the next one (vanilla closed it); only Escape, or the player closing the chat, swaps back to the feed. Sending a command (anything but the chat's own `/msg`, `/tell` and `/w`) brings the Console forward at once — its window is raised, the console becomes that window's front tab and takes the input, and a console the player had closed is reopened first — so the answer is already in view when it arrives. That is client-side presentation only: the command itself takes the game's normal path to the server. Text typed into the input is not lost when the screen is closed or resized: the unsent draft is kept (per session, cleared on disconnect) and restored the next time the chat opens, unless the screen was opened with its own default text such as `/`; sending a message or command spends the draft. Drafts belong to the tab they were typed in: switching tabs or windows puts the field's text away with the tab just left and brings back whatever the tab coming to the front had unsent, so a half-written whisper does not follow you into Global. Typing `@` shows a completion list of the server's roles followed by the online players (yourself first, then alphabetical), filtered live and accepted by click, Up/Down, Tab, or Enter, exactly like the emoji completions. Each player's row wears their face, drawn on the same rules as the heads in the message lines; a role has none and is named in its own colour instead. Addressing a role — `@Operator` — is a mention for everyone holding it: the server states which roles a player holds alongside the chat access it already sends, and each client checks its own, exactly as it checks its own names. Only roles that name people expected to answer can be addressed — the Developer mark is worn and never called — and they answer in every channel, role-play ones included: an operator is worth calling wherever the call is made, so the completion list offers the roles, the colours resolve, and a holder is pinged whichever tab the call was typed in. Inside a message every `@name` that reaches somebody is drawn in the colour of the identity it names, exactly as that identity signs its own lines: a role its own colour, an account its primary role's, and a mention that names a character — by the character's name, or by the account on a channel whose lines are signed in character — that character's starting-faction colour, self-mentions included; the words around it stay as they were typed. Only when none of that resolves — a role-less account named on an account channel, or a player whose character this client does not know — does the shared honey stand in, so a mention is never invisible. All of it goes through one resolution (`ChatMentionColors`); the completion list and the input bar colour the same name the same way, so it reads alike while it is typed, while it is offered and once it is sent. Which roles a name wears comes from the lines the server signs with them and from the role roster the chat access now carries — every online role holder with their mask, refreshed on each join and leave — so a role holder's mention wears their colour before they have spoken, your own included. Each online player appears once: in OOC the list shows and inserts the Minecraft account name, in role-play channels the active character name, but typing either name finds the player (`@Steve` and `@Aragorn` both offer `Steve123` in OOC and `Aragorn` in Global). The pairing of account and character comes from the public appearance sync the server already sends for every online player (it now carries the account name), so the list never guesses from display names. Mention detection is purely client-side presentation (each client checks its own names), and `client.enableChatPings` turns the whole feature off. While the field holds a message (not a command), the client tells the server every 2.5 seconds that it is typing into the selected tab, and once that it has stopped when the field empties, the tab changes, the message goes out or the screen closes; the server relays the presence — the name the message would show, never any text — to exactly the players who would receive a message sent there now, under the same checks, and to nobody for a command, an NPC conversation or a channel the player cannot send to. Each window shows *Name is typing…*, two or three names, or *N people are typing…* in its trailing strip — the line between the newest message and the bottom rule — for its front tab, only while the view rests on the newest message: a view scrolled back hands the strip to the history and the typing line fades out with the first turn of scroll; a name not refreshed for six seconds drops out on its own, so a lost stop never leaves a ghost. `client.sendChatTypingStatus` and `client.showChatTypingIndicators` switch each side off for this player; `chat.typingIndicators` switches the relay off for the whole server.

Messages from one identity **group**, Discord-style (`client.enableChatMessageGrouping`, on by default) — players and NPCs alike: a message arriving within two minutes of the previous one from the same sender speaking as the same identity in the same tab (an NPC's next speech in its conversation included) drops the repeated header — the channel prefix, tags, brackets, head, name and title — and keeps only its own timestamp in the column and the body, which starts on the anchor exactly where a wrapped continuation line starts; in the closed feed a run therefore names its channel once, on its header line, instead of repeating it on every continuation, so a run reads as one voice speaking in paragraphs. A run is strictly consecutive **in the view it is read in**, and no two views need agree: a message printed between two of a sender's messages ends the run only where it is actually shown, so Player A's two Global messages stay one run in the Global window while Player B's OOC message between them splits them in the combined feed. How long a run stays open is the view's too, because the views do not keep a message for the same length of time — and either way the span is measured from the message that *opened* the run rather than from the one before, so a run is a burst with one header at the top of it rather than a chain a slow speaker can extend for ever. A window is a scrollable log, so its runs hold for two minutes, measured from the message that *opened* the run — a burst gets one header, and one speaker cannot extend a single run all evening. The closed feed measures from the message *before* instead: it fades a whole run at once on the clock of its newest message, so the group is on screen for exactly as long as that message is, and anything arriving inside the ten-second fade joins it however long the run has already been going. Only silence long enough for the whole group to go — or another voice, or another channel — starts a new run there. The feed also fades a run **as one** rather than line by line — every line of a run is drawn on the clock of the run's newest message, so a group arrives, sits, and leaves together, and a message that joined a run late is still readable for the full ten seconds. A run therefore lives at most twice the fade before it is gone. A grouped line starts on the anchor exactly where a wrapped continuation line starts, in both states. An appearance switch ends a run everywhere (the identity name changes), a line with no sender identity at all — a system line, an adopted stray, a vanilla print — ends it wherever it lands, and every message still pings, tints, counts and copies on its own. Nothing about the grouping is stored on the message: vanilla's history keeps every message in full, `ChatGroupRuns` keeps the sender identity it was signed with beside the headerless form of the same line, and each view runs the one rule over the sequence it shows — which is why the closed feed lays its own lines out (`ChatWindowLines`) instead of reading the shared list. A message may be typed with light **markup**, shown but never stored: `**bold**`, `*italic*`, `~~struck~~`, `` `code` `` and `||spoiler||` (`ChatMarkdown`). The wire, the copy text and the server's log keep exactly what was typed, markers and all — the markup can only change how a message reads, never what it is. A marker opens only against text and closes only against text, so `2 * 3 * 4` is a sum rather than an italic, and anything that is not a complete pair stays the characters it was typed as. Marks nest, and a two-character marker closes at the end of its run of that character, so `**bold *and italic***` unwinds in the order it was opened. Code is literal inside — no emoji, link or mention is read there, since reading it again is the one thing quoting it says not to do — and is shown in the palette's rose gray. Bold, italic and strikethrough become vanilla's own decorations, so the wrapper measures and the renderer draws them without knowing markup exists; a spoiler is drawn obfuscated, Minecraft's own way of showing text that is there but not to be read. Plain web addresses in a message become **links** while Minecraft's chat-links option is on: a whole `http(s)://` word, underlined in the palette's blue, opening through the same confirm dialog every other chat link uses; trailing punctuation stays text, and with the option off addresses stay plain text exactly as vanilla leaves them. With the chat screen open a message reads `<HEAD CharacterName, the Faction Title> Message`, its `[HH:mm]` timestamp standing apart in the timestamp column; with it closed the HUD shows every channel in one feed and prefixes each line with its channel, `Global: [HH:mm] <HEAD CharacterName, the Faction Title> Message`. A titled sender is named the way LOTR names its NPCs (`entity.lotr.generic.entityName`, `%s, the %s`): the character name, then `, the ` and an epithet made of the name of the sender's people and their LOTR title — `Aldric, the Gondor Farmer`, or `Aldric, the Farmer` when the faction is unknown. The server sends the title and the faction name separately (the faction name is appended after the original wire layout); the receiving client composes them through `chat.losttales.title.epithet` (`%s %s`) and `chat.losttales.title.suffix` (`, the %s`), so the wording is localizable, and marks the suffix with a title marker carrying its colour and the bare epithet. A sender without a title is shown exactly as before — no comma, no "the", no faction. The people are not always named after their realm: a Lothlórien character is a *Galadhrim* Miner, a Rohan one a *Rohirrim* Miner, a Dunland one a *Dunlending* Miner. LOTR exposes no such field — its faction strings are the realm's name and a plural collective ("Elves of Lothlórien"), neither of which reads as an adjective — so the exceptions are a table of our own in `FactionDemonyms`, keyed by faction code name and localizable (`losttales.faction.demonym.LOTHLORIEN=Galadhrim`), following the names LOTR's own NPCs already carry ("Galadhrim Warrior", "Dúnedain Blacksmith", "Dalish Baker"). A faction with no entry keeps its display name, which is right wherever the realm's name is also the adjective (Gondor, Mordor, Dorwinion), so only the exceptions are listed and a faction added later needs nothing. The server resolves it when it builds the line, in the same field the faction name always travelled in. On account lines — OOC, Operator, Console, Discord and whispers, where the sender is the Minecraft account rather than a character — the line opens with a tag for every account role the sender holds, ahead of the name, and the name itself takes the primary role's colour: `[Operator]` in the palette's crimson for a server operator and `[Developer]` in mulberry (`#7C3D64`) for a member of the Lost Tales team, Developer first when both apply (`chat.losttales.tag.operator`, `chat.losttales.tag.developer`). The roles live in one place, `ChatAccountRole` — precedence, tag key, colour, and the rule every account line's name colour comes from (`ChatAccountRole.nameColor`: the primary role's colour, the chat's ivory without a role). The server resolves the roles when it builds the line — operator status from its own permission check, Developer from the recognized-user catalogue `ELostTalesUser` keyed by the authenticated account id — sends them as a role mask and takes the name colour from that same rule, so the client never decides who is staff and has no role-specific branches. The rule holds wherever an account line is built, the channel it goes to notwithstanding: a whisper is tagged and coloured exactly as an OOC line is. Recognition is cosmetic only: nothing in `ELostTalesUser` grants a permission, and on an offline-mode server the name-derived ids match nobody. Role-play lines never carry a tag or a role colour. Titles appear only where Lost Tales draws its own chat lines and their hover card; vanilla and third-party name rendering is untouched. The prefix is built once and skipped at draw time while the tabs already separate channels. Channel names use normal title casing, and Faction uses the active faction's exact color. The invisible head marker reserves exactly the icon width; there is no extra visible padding inside the brackets, and both brackets use the character name's exact RGB color. Clicking the displayed name opens (and selects) a whisper tab with that account, including for character channels where the visible role-play name differs from the Minecraft account name. While chat is open, hovering the rendered head or name shows a bounded player card; the sender's identity is one hover span — opening bracket, head, name, title and closing bracket, the hairline gaps between them included — so the card never blinks out between two glyphs. Its first line is `Character Name (Account Name)` for a character identity and just `Account Name` for an account identity (OOC lines, players without a character) — never empty parentheses. Below it, each of race, faction (the character's selected starting faction, never alignment or reputation), level, gender, age, and the biography is shown only when known, the biography wrapped to the card and bounded to a few lines. The details come from the public active-character appearance the server synchronizes for every online player — the appearance sync now carries starting faction, level, age, and description alongside name, race, gender, skin and capes, all appended after the original wire layout — and are shown only when they describe the character the line names, so a historic line never borrows a later character's details. An account identity names no character at all, so its card is the account alone — name and head, never the race, level or biography of whatever character its player happens to have active.

While the chat screen is open, a row of folder-style tabs stands on top of the topmost visible message (on the baseline when the view is empty), riding along with the stack as messages arrive and as the history enters — one per channel that is open in that window and currently available to the player. The tabs stand side by side with a one-pixel seam, like a browser's; the selected tab comes forward, lifts slightly, and runs into the box, and each tab's top edge carries its channel's colour, full at the centre and fading out to both ends. Every tab wears an icon before its name (`ChatChannelIcons`): an emoji per channel — Global wears the slight smile, OOC the zany face, Party the joy, and so on — except Faction, which wears the LOTR banner item of the active character's faction (resolved through LOTR's own faction-to-banner registry in `LotrFactionBannerResolver`, cached per faction; a faction LOTR gives no banner shows the Banner of the Stewards of Gondor, and without LOTR's banner item at all the tab falls back to its emoji), and a head for conversations: the partner's own head for a whisper with a player the client can place (in the world or in the appearance sync), the NPC's portrait for an NPC conversation, remembered from its speech for the session; a whisper whose partner is not placeable yet wears the blush emoji, an NPC whose portrait has not been seen the grinning one. The icon is drawn at the sprite's own size, centred in a resting tab's interior with a clear row above and below it, the label and controls centred with it; the selected tab's lift carries all of it up rather than re-centring it. A decoration only. Clicking a tab selects it; with an empty input, `TAB` (or clicking the `[Channel]` indicator beside the input) cycles the open channels in window and tab order. With text or a command present, `TAB` is command completion, and the suggestions belong to the input they were asked from: the request takes vanilla's path (client commands complete locally, everything else is asked of the server), and the candidates appear as a **popup over the input**, exactly like the emoji, mention and share completion lists — never as a chat line, so nothing lands in any history or feed, nothing opens or fronts the console, and nothing counts unread. The common prefix still completes in place first; when several candidates remain the popup lists them (up to eight, more folding into a `+n` count), and repeated `TAB`s walk them exactly as vanilla cycles, `Up`/`Down` walk them either way, a click picks a row, `Escape` closes only the popup, and any other key dismisses it. An answer that arrives after the selection has moved to another tab is dropped, since the field by then holds that tab's draft. A submitted command is unchanged: its actual output is console output and still brings the Console forward. The selected channel decides both which history is shown and where a new message is sent: each tab shows only its own channel's messages and keeps its own scroll position, which survives closing and reopening the screen. A line printed straight into the chat without passing through the received-chat event — a game-mode change notice, a saved-screenshot line, another mod's local print — is noticed within a tick and adopted into the console: rebuilt in place as a console system line with the channel prefix, timestamp and a tracked id, so local prints read exactly like routed console output; only a line printed under a deletable id of its own is left untouched (its printer may still replace it by that id) and simply rides with the Console tab. A window — its history, backdrop, tabs and input bar — is one motion group: opening the screen brings it in with the same sampler, easing, direction and duration every other Lost Tales screen uses (`client.guiAnimation*`), the tabs and bar taking their position from the bands the history drew and their opacity and motion from the same sample, so they enter, settle and fade together; the bands are recorded from the first frame of the fade, while the lines are still too faint to paint, so the tabs are there from the start rather than popping in once the lines become visible. Opening a tab that received messages while you were away shows Discord's kind of **unread divider**: a whole row of its own between the last read message and the first unread one (everything older shifts up by it), a crimson rule on the row's centre that is strongest beside the date standing in a gap at the middle and falls off to nothing at both sides, starting clear of the timestamp column. It stays while the new messages are being read, and it is gone once they have been seen — the tab is left, the screen closes, or you send a message there yourself, the way Discord's goes — with the next unread run bringing a fresh one. The date stands three pixels clear of the rule on both sides, and each half's strongest, innermost pixel carries a small cap — one pixel above and one below — so the rule opens toward the date. A view scrolled away from the newest line grows a small **jump-to-present** button — a square with a downward arrow at the panel's right edge — flying in from below the bottom rule — cut on the rule by the same clip that cuts a scrolling line, so it genuinely emerges through it — and sliding back out the same way when the view is home; hovering names it (*Jump to Present*) and clicking it glides the view to the newest message with the same eased motion the wheel scrolls with. A tab that received messages while another tab was selected shows textual counters after its name: `Gondor [2] [5]`, where the first, salmon-coloured `[p]` is the number of unread messages that mentioned you and the second, honey-coloured `[x]` the number of other unread messages; a message is counted once, as a ping or as unread, never both. A counter appears only while its count is positive (`Party [3]` with no pings), caps at `[99+]`, updates as messages arrive, and clears once the tab is viewed. The counts live in `ClientChatChannelViews`, the single source of unread state; a closed channel keeps counting, and the `+` menu shows the same count beside its name (`Trade [3]`). With the chat screen closed the windows are not drawn at all; one *feed* shows every unmuted channel's messages, whether or not the channel has a tab (with their channel prefixes), as a single fading stack at its own position, so nothing is missed. It is as tall as the whole message lines that fit in a third of the screen (`ChatWindowPlacement.feedLineCapacity`), measured with the stride the renderer draws them at, so it grows with the screen and the GUI scale without any line changing height and the remainder is left as margin rather than spent on a line that would be clipped; the box still shrinks to the messages it actually holds. Windows are unaffected — they follow their own height or the game's chat setting. Every message the server distributes carries an **id** of its own (`ChatMessageIdAllocator`, appended to the message packet's layout; what the numbers mean is `ChatMessageIds`): milliseconds since the epoch kept strictly increasing, so it is roughly the time the message was sent and always in the order the server accepted them. A chat line id is each client's own and is reused as its history trims, so anything that names a message afterwards — a reply, an edit, a moderator's removal — names it by the server's id instead, and `ClientChatMessageIds` crosses between the two in both directions. A whisper's two copies share one id, since they are one message. Zero means a line nobody can name (a system notice, an adopted stray) and negative ids belong to the client, for the lines it writes itself in an NPC conversation and never sends anywhere; a negative id arriving over the wire is malformed. A message may also **reply** to another, and the quote travels with it: only the server knows whether the replier could see the message they named, and only the server can promise every recipient the same quote — one who joined after the original, or whose history has trimmed past it, has nothing of their own to quote from. `ChatMessageLog` remembers the last 256 messages it distributed *and every account it sent each of them to*; a reply request naming an id is honoured only while that message is still within reach and the replier was one of its recipients, so naming an id can never quote a private message back into a channel of the replier's choosing. Who could see a message is a fact about the moment it was sent — a party since joined, a proximity call since walked into — so the recipients are recorded rather than re-derived. A reference that fails either test is dropped with a notice and the message goes out on its own; one that passes is sent as a `ChatReplyReference`: the id, the author, and the message cut to one glanceable line. Messages are never copied; the views are filtered indexes over vanilla's own history, described by a `ChatLineFilter` (a set of channels, with the console's untracked lines) and cached per filter. That history keeps `client.chatHistoryLines` messages (1000 by default, 100–5000) rather than vanilla's hundred: the coremod replaces the literal in `GuiNewChat`'s own trimming with the configured capacity, so a long session stays scrollable in every tab; the history still belongs to vanilla and goes with the world on disconnect. **Character selection.** Identity no longer gates a channel: anyone talks anywhere, and *which* of the player's identities a line is signed with is chosen from the character-selection button — the player's own head over the chat's standard shadow, first on the input bar, left of the channel indicator. Clicking it opens the **Character Selection Menu**: its top row shows the character the selected tab currently speaks as — head and name — with the lock control beside it, wearing the same open and closed padlock sprites and hover states as the window lock and answering with the same kind of tooltip; below it the account and every character of the player's roster, ordinary and lore characters under their own headers, each with its head, the effective one marked in the mention honey. Every channel keeps a default — the account channels (OOC, whispers, Operator, Discord, Console) the account, the role-playing channels the active character (the account when there is none) — and switching channels drops an explicit choice back to that default, unless it is locked: the lock beside the selected character holds the choice across channel switches until it is unlocked (toggling it keeps the menu open, its rows refreshed), and the padlock rides the button's corner while it does. The choice travels on the send request as a request only (`APPEARANCE_*` on `LostTalesChatSendPacket`): the server resolves the character id against the sender's own roster — nobody can wear anyone else's character — refuses an id the roster does not hold, and signs the line itself: name, title, faction colour and skin from the chosen character, roles and the account head for the account, so heads, cards and mentions all follow the line's identity rather than the channel's (`isAccountLine` on the message packet). Membership still rules routing: Faction and Party follow the *active* character's faction and party whatever the line wears, and stay closed without them. A conversation is with a person **as they present themselves**, not with the account behind them: whispering someone speaking as Aldric and whispering the same player speaking as Beren are two conversations, and neither is the one with their account (`ChatTab` carries both, keyed by the identity, and a tab id stored before identities existed still reads as the account's own). The account is still who the line is routed to and is always reachable, so a conversation never stops working because someone switched character; the identity is a request the server checks against that account's own roster before filing anything under it. Each party's copy is filed under the *other* party's identity. A whisper spoken as a character names the account in brackets behind the appearance — `Aldric (Steve123)` — on the line and on the conversation's tab, which follows the partner's latest appearance in name and colour; in the closed feed a conversation's prefix names the channel — `Whisper:` — rather than the partner, since the line itself already opens with the sender. The indicator still shows a channel the player cannot send to (Faction without a faction, Party without a party) muted, and Enter shows a notice instead of sending. An empty channel draws its full panel — backdrop, timestamp column, separator and shades — through the same path a filled one uses, with a small rose-beige invitation line where the newest message would be, so the first message changes nothing but the words: no backdrop pops in around it. That row is a message's row, so the hatch stops above it rather than running under the words. Rows the history does not reach yet — a fresh channel, or a window taller than its few messages — wear a faint diagonal hatch (the 16×16 hatch cell of the chat's own sprite sheet, `textures/gui/chat.png`, tiled in the two ivories it was authored in, so its own shading reads rather than being flattened to one tone; half opacity across the middle of the hatched region and falling off linearly to nothing at its top and bottom, so the fill has no edge of its own to read as a border) whose lower edge follows the stack's top exactly, so the region reads as holding no messages rather than as a gap; a view with enough history to scroll has no such rows and never shows it. The tab row only appears once the open view has at least one line; Tab and the indicator still switch channels before that. Hovering a row of the mention completion list shows the same player card as hovering a name in chat. The Faction tab, indicator, and message prefix show the active character's LOTR faction name (for example `Gondor`) rather than the word "Faction"; the logical channel and its routing are unchanged, and the catalogue name is used if LOTR cannot resolve the faction. A system line that names a player names them as the mention they are: an achievement's, join's or death's name component becomes @Name for every player this client can place — on the character channels showing the account's active role-playing character, the identity every ordinary line there is signed with, in that character's own name colour (its starting faction's, exactly as the character's own lines wear it), with the role or shared mention colour kept where no character is known — and an NPC speaking the player's name gets an @ put before it. A line naming this player highlights, counts as a ping and sounds the cue (unless the channel's mentions are muted) — except that achievement lines are announcements, not someone addressing you: their mention still highlights and counts, but stays silent. The cue itself sounds from one place, and pings landing within a fifth of a second of the last one — two mentions in one tick, an achievement burst — collapse into a single chime while every visual ping still shows; pings far enough apart to read as separate notifications stay separately audible. Every player mention — typed with an @, or made one this way — answers to the pointer like a sender's name: hovering shows that player's card, clicking opens the conversation with them. The message the pointer rests on lifts a faint shade — the same tone a popup's hovered row wears, laid over whatever the line already shows rather than replacing it, so a mention the pointer is on still reads as a mention. A *message* is what the pointer is on, not the one wrapped line under it, so every line of it lights together; the closed feed has no pointer and never does. Nothing is hovered while a menu is open or something is being dragged, since the pointer is on that instead. It also grows that message's own **toolbar** at its top right — reply to it, and copy it, the same two the menu offers, where the pointer already is. Reply is left out for a message nobody can answer, so a console notice shows only Copy and the toolbar simply narrows. The toolbar is drawn in the stack's space, so it rides the scroll with its message, and inside the message's own top row rather than floating above it: the row under the pointer is what keeps the message hovered, and a toolbar reaching past it would hover the message above and take itself away. Its screen rectangle is recorded from the draw, like the jump-to-present button's, so the click and the pixels cannot disagree. Its controls are glyphs and say nothing on their own, so hovering one names it (*Reply*, *Copy Message*) in the same tooltip the jump button uses and with the same words the message's menu offers; the button is asked after the jump button, which is drawn over it where the two meet, and from the front window back, so the tip names the control a click would actually reach. Right-clicking a visible message opens that message's own menu — **Reply**, and **Copy Message**, which copies only the message body and briefly confirms — except over the sender's identity span or a mention, wherever a card is showing: there the click belongs to the person and nothing opens. What the menu acts on is resolved while the pointer is still on the line, since by the time an entry is chosen it has moved to the menu. **Message *Name*** opens the conversation with the identity that message was signed with — never with a Discord speaker, who belongs to somebody this server cannot reach, and never with yourself. Reply is offered only for a message the server named and only in a channel you may send to, so a console notice, an adopted stray and this client's own NPC lines are nobody's to answer. Choosing it moves to the message's own tab and stands a **Replying to Name** chip in the window's trailing strip, where the typing line goes — the chip takes the strip while it shows, since what you are answering matters more, while you are answering it, than who else is talking. The chip carries a cross, and the whole of it answers to a click so a near miss still drops the reply — and names itself (*Cancel Reply*) wherever it answers, so what the tooltip covers is exactly what the click does; Escape drops it too, before it closes the chat, and so does leaving the tab it was started in. Sending spends it: the next message is a message of its own. **Edit Message** and **Delete Message** are offered on your own messages alone, and only on ones the server named — never on a line from the Discord bridge, whatever name it carries. Editing puts the message back in the input bar as it was *typed*, markup and all rather than the line as it reads, and stands an **Editing message** chip in the same strip the reply chip uses; the two never both hold it, and Escape, the chip's cross, or leaving the tab puts it down. Sending sends a correction to that line rather than a new message: it is rewritten where it stands, keeping its place in the conversation, and wears a quiet *(edited)* after the body. Deleting asks first, since it takes the message back from everyone who was sent it. Neither happens on the asking client's say-so: the server checks that the account asking is the one that wrote the message and that the message is still within the log's reach (its last 256, the same reach a reply has), revalidates the new text exactly as it would a fresh one, and then tells precisely the accounts the original was sent to — so the line changes on every screen showing it, for the same reason and at the same moment, and on no screen that never saw it. A message carried to Discord is not changed there: the bridge writes through a webhook and keeps nothing it could go back and edit with. A message of your own is on screen before any of that: it is drawn the moment it is sent, faint, and the server's own copy takes its place where it stands rather than arriving underneath it — so the conversation answers the keyboard instead of the round trip. The faint line is a promise and not yet a message: it carries no server id, so nothing that names a message by id (a reply, an edit, a quote) can name it until it is confirmed. The client sends a name of its own along with each message and the server hands that name back on the sender's copy alone, which is how the two are matched; it means nothing to anyone else and is stripped from every other copy. A promise the server never answers within ten seconds is marked *(not delivered)* rather than left sitting faint, so a message that went nowhere — a whisper to someone who has just logged out — is visibly one. Clicking the quote a reply opens with takes the view to the message it quotes and lights that line for a moment in the palette's honey, so the eye finds where the view landed; it lands near the middle of the window rather than at its edge, so what was said around it is readable too. The quote names its message by the server's id, and which line that is drawn on — if it is still drawn at all — is the client's own business (`ClientChatMessageIds`): a message the history has trimmed past, or one in a channel this window does not show, says so rather than moving the view somewhere arbitrary. Addressing a role — hovering `@Operator`, or the `[Operator]` tag an account line opens with (the worn-only `[Developer]` included) — shows the role's own card: the role's name in its colour, what the role is, and every online account holding it, straight from the roster the server sends with the chat access (refreshed on every join and leave, and re-checked once a minute so a mid-session `/op` or `/deop` — which fires no event a mod can hear — reaches every card within the minute), so the list is the server's word rather than a guess from who happened to speak; clicking a role mention or tag opens no conversation, since a role is nobody in particular. Chat and the other Minecraft GUI screens use the same Lost Tales cursor as the LOTR map.

Every overlay the screen draws — tabs, the channel indicator, the emoji, item, marker and quest buttons, the completion lists, the pickers — registers the rectangle it actually painted for that frame (in screen space, whichever motion group drew it), and hover, tooltip, and click handling check that record before touching the message stack. While the pointer is inside an overlay, the lines underneath are neither hovered nor clickable, so no hover card, item tooltip, or link click can fire through a popup; because the record comes from the draw itself, visual and interaction order cannot disagree. Chat lines are hit-tested the same way: the draw pass records the exact screen band of every line it draws (scroll, chat scale, view filtering, and entry motion included), and the hover card, component tooltips, clicks, and right-click copy resolve against those bands.

`chat.proximityRadius` is a server-authoritative gameplay setting. Timestamp visibility, the emoji toggle, and the message, input-bar and selector animation settings are client presentation preferences under the `client` category. A new message eases upward and slides in from the left with a short fade, briefly overshooting its resting position to the right before settling. Vanilla's chat hit test (`GuiNewChat.func_146236_a`) is routed through the drawn bands by the coremod while the Lost Tales chat screen is open, so LOTR's achievement hover card and any other mod asking vanilla where the pointer is get the same answer as Lost Tales itself, and get nothing under a popup. Disabling animation does not alter layout, routing, history, or command behavior. Every shadow in the chat — under text, sprites, heads, icons and controls alike, in every window and on the input bar — is the palette's plum black (`#2d1e2f`) at half opacity, one pixel down and right. That is not left to each call site: every chat draw first turns blending on, because `Gui.drawRect` (which every panel, strip and bar is built from) switches it off when it finishes, and anything drawn afterwards would land opaque. Chat surfaces — the message backdrop and the input bar included — use the same plum black at half opacity; the message backdrop fades to transparent over its final third, while the input bar is solid across its width. Message content is cut only on the window's two rules: below, a glyph's descender or shadow under the newest line, and a stack sliding down under a scroll, continue into the trailing strip and disappear behind the bottom rule; above, two pixels of head-room separate the top rule from the topmost line's glyphs, and that head-room belongs to the topmost line itself — its band, a mention's dark-mulberry tint above all, extends up through it to the rule rather than being cut flush on the glyphs. The scissor converts GUI positions with the scale factor the GUI projection itself maps by, so the cuts land on the very display rows the rules are drawn on at every window and display size. The menus, for their part, are freed from vanilla's thirty-frame cap (a coremod literal patch on `Minecraft.getLimitFramerate`, following the player's own framerate limit), so the Lost Tales pointer moves as smoothly on the main menu and every other screen as it does over the chat. The window carries two one-pixel ivory frame edges inside its own footprint, each one linear ramp along its whole length: the input bar's last pixel row, strongest at the left and fading rightward, and a column just inside the left border, strongest at the bottom-left corner and fading upward. The bar owns its stretches of both — its last row and the column beside it — drawn over its own fill so nothing darkens them, arriving with the bar's fly-in; the column's remainder above the bar is drawn with the window on the same ramp, so the two stretches read as one unbroken edge. They are part of the window's box, so a window dragged flush against the screen border keeps them on screen. Each window has its own input bar directly under its bottom rule — no gap — as tall as the tab row and exactly as wide as the window (the chat width setting at the chat scale, fade disregarded), everything on it centred in its height. Right to left it carries a send arrow (so Enter is not the only way to send), the emoji button, a chevron, and the item, marker and quest buttons, their pickers opening just above the bar at one size wherever the window sits (smaller only when the screen has no room above). The chevron folds the three insert buttons away to the left, panels and all — the emoji picker stands outside the fold — and the choice is kept in the layout file (`toolbar collapsed=`). Left of the send arrow a small `37/256` counter counts the message's visible characters, drawn near three-quarter size in the timestamp's sand — the scale snaps so every font pixel is a whole number of display pixels (half at GUI scale 2, two thirds at 3, full size at 1), so the digits never show mixed-size pixels; the field refuses input past the limit (a paste is trimmed back to it), and the counter turns salmon when it is reached. Selecting text in the field lays a translucent steel-blue wash over it — emoji and token previews included — instead of vanilla's colour inversion, which turned sprites into their negatives. The bar of the window holding the selected channel carries the indicator, the text field and the toolbar; the other windows show their bar with the name of their front tab dimmed — followed by that tab's unsent text, if it has any, so a draft stays in view where it was typed — and a click in it moves the input there.

## Discord

The server can bridge one Discord text channel to a **Discord** chat channel (account identity, everyone online reads it, steel blue, the Discord emoji) with the mod's own bridge — no bot library, no plugin, no hybrid server. It is server-only configuration under `discord` in `config/losttales.cfg`: `enabled`, `botToken` and `channelId` for reading Discord, `webhookUrl` for posting to it, `pollIntervalSeconds` (2–60, default 3), and `relayGameChat` / `relayDiscordChat` to switch either direction off, and `avatarUrlTemplate`, the picture each post carries (`{name}`/`{uuid}` of the sender's account, a public head service by default). The step-by-step setup is on [Discord_Bridge](Discord_Bridge.md). The token and the webhook URL are secrets: they stay in the server's file and are never logged or sent to a client.

Game to Discord: a line written in the Discord channel is delivered to players like any other and then queued for a worker thread, which posts it to the webhook under the sender's name and head with mentions disabled, so nobody in Discord can be pinged from the game. Discord to game: the same worker polls the channel through the REST API with the bot's token (the bot needs access to the channel and the Message Content intent), reads only what arrived after the server started — history is never replayed — drops bot messages (the webhook's own posts among them, so nothing echoes), spells Discord's markup out (`@name`, `#channel`, `:emoji:`), flattens line breaks, strips formatting codes and cuts to the chat's length, and hands the result to the server thread, a few per tick, which sends it to everyone online as a Discord-channel line under the Discord display name with a fixed sender id the clients recognise: such a line — and its hover card — wears the Discord emoji where a player line wears the sender's head, drawn 1:1 — never scaled — in a head slot declared two pixels wider than a player's, so the mark keeps the same clear pixels either side that every head keeps; a bridge sender never masquerades as the default skin, and no skin lookup is ever made. A refused token or missing permission stops reading for the session with one severe log line; a rate limit is honoured for exactly the time Discord asks; any other failure backs off, doubling up to a minute, logged once on the way down and once on recovery.

The Discord tab exists only while the server says the bridge is on: the same access packet that states operator status now states it, so a client never shows a tab the server would refuse, and the server refuses the channel with a notice when the bridge is off.

## Chat windows, tabs and layout

The tabs are not fixed. The layout is one model, `ChatWindowLayout`: a list of windows, each an ordered row of channel tabs with a front tab, a lock and a position, plus the set of muted channels. Every window is equal. The default layout is two of them: a console window (Console, Operator) in the top-left corner and a conversation window with every other channel in the bottom-left corner. A window that loses its last tab disappears, and the last open tab of all can never be closed, so there is always somewhere to type. A channel lives in at most one window, and a channel in no window is *closed*: its tab is gone, but it keeps receiving, keeps its history, unread count and mute setting, and stays in the feed unless muted. The in-game chat screen, the closed-chat overlay and the HUD placement editor all read and write this same model, so a window moved in one place is exactly where the others find it. Everything the chat knows about the messages on screen — which tab each line belongs to, the open conversations, the scroll offsets, the shared items and markers — belongs to a server rather than to a connection: leaving and rejoining the same address (or the same single-player world) keeps the history and its tabs, and arriving anywhere else starts clean, the game's own message list included. A client cannot be told that a server restarted, so a restart while the client stays running leaves the old messages in place until the client is closed.

- **Reorder** — drag a tab along its row. **Detach** — drag it clear of the row (about fourteen pixels above or below it) and release: the channel becomes a window of its own, its row landing under the pointer. **Dock** — drag a tab onto another window's row; a honey insertion mark shows where it will land. A press that moves less than four pixels is a click and just selects the tab; Escape cancels a drag. A window whose only tab is dragged out simply moves; a window whose last tab is docked elsewhere or closed disappears (the last open tab of all cannot be closed). There are at most eight windows.
- **Move a window** — drag it by the dotted grip at the right end of its strip or by the empty strip beside it; its messages are not a handle, so a click on a line stays a click (only the grip's own glyph lights up and offers *Drag to move*; the bare strip drags without saying so, and the glyph stays lit for as long as the drag lasts, wherever the pointer has gone). A press anywhere in a window — its strip, its messages, its bar — makes it the window being typed in, and so does dragging or resizing it; the pointer shows the click pose over any window that is not already that one (a press that does not travel four pixels stays the click it always was: links, names, right-click copy); the row, the lines and the bar move as one piece: the row and bar are drawn on the same fractional position the lines are. The drag follows the raw mouse in fractional pixels, so it glides rather than stepping by whole GUI pixels. A window is anchored by its baseline — the edge its newest message sits on — with messages growing upward and its input bar hanging below, so it never moves when a message arrives; the box is only as tall as what the window currently shows, so a window with a few lines can be placed anywhere, the top edge of the screen included A window parked high that later fills up is pushed down just far enough to keep its top on screen — it grows downward from there — and returns to its anchor as its lines go; the stored position never changes. Windows keep off the screen edges only — the same four-pixel margin every HUD panel keeps — and may overlap one another, in the chat and in the HUD placement editor alike: the window in use (the one holding the selected tab, or the one last dragged) is drawn in front and is the one the pointer reaches first; a growing window never loses lines to a neighbour. Only a window *linked* above it moves up with it, until that one meets the top of the screen. The stack's rise on a new message plays only while the window is still growing. A window none of whose channels the player can currently see (a Party window outside a party) is not drawn, does not appear in the HUD placement editor, and stands in nothing's way. It is all recomputed every frame from the stored anchors and undoes itself as lines go.
- **Resize a window** — an unlocked window is resized the way any window is: press just outside any of its four edges or corners and drag. The pointer says what the edge would do — a double arrow across an edge, a diagonal one at a corner — and the window itself follows the drag: its temporary dimensions are written into the layout unpersisted, so its history reflows and redraws live at the size under the pointer, nothing is saved or synchronized while the drag is in progress, releasing the button commits the dimensions to the layout file once, and `Esc` cancels the drag and puts the dimensions from before it back exactly. The dragged edge follows the pointer continuously — there is no snapping back to the starting size, and the whole-line rounding of the room lands on the far edge, never under the pointer. The resize border and the tab strip overlap along a window's top edge, and one hit test decides between them for the hover pose, the press and the drag it starts: what is drawn above the windows (pickers, completion lists, the settings menu, the input bar group) owns the pointer first, the resize border next, the strip and the window itself last. What the pointer shows is therefore always what the press does, and the interaction a press starts is held until the button comes up. The edges the drag does not hold stay exactly where they are, and neither size may leave the screen; there is no screen margin — a window may be dragged and resized flush against the border, like every HUD panel. A stored size the current screen cannot hold — the GUI scale changed under a window resized large, or the game window shrank — is capped while drawn to what fits inside the screen, width and wrapping together so no line runs past the edge; the stored size itself never changes, so scaling back restores the window exactly. Nothing changes size but the window: the text, the icons, the tabs and the bar keep theirs, and a bigger window simply shows more lines and longer ones. **Every window has its own size.** Its height is continuous, exactly like its width: the window keeps the pixel height it was dragged to rather than snapping to a whole number of lines, and the line the room ends inside is drawn and clipped cleanly at the window's own edge (the layout file records the height in message lines and fractions of one, `lines=12.37`, bounded by the screen and by the layout's own limit of 64; nothing rounds the room anywhere, so no edge of the box ever wobbles against another while a resize runs, and while one does the scroll follows its clamp rigidly instead of gliding after it). That height decides how many lines the window shows and how far a page of scrolling moves, and it replaces the game's chat-height setting for that window. The clip is a scissor rectangle in display pixels, so it is exact at every GUI scale and window size, and the window's tab strip stands on the same edge the clip cuts at, at every chat scale. Its width is its own too: Minecraft lays a message out once, at one width, so every view lays its lines out again for itself (`ChatWindowLines`, cached per view and rebuilt only when its width, the colour setting, the drawn state or the history changes) — a window at its own width when it has one, and always for the open state, which draws no channel prefix and so hands that width back to the message body instead of leaving it blank at the end of every line. The feed is laid out there too, at the game's own chat width and with the prefix, since its grouping is its own even though its wrapping matches the shared list's exactly; a window's size and wrapping never affect it. A client that cannot read the unwrapped history falls back to the shared list, where every message keeps its header. Neither size may go below what leaves a window readable: 160 chat units wide (scaled with the chat scale, so it is the same amount of text at any of them) and one message line tall.
- **Sticking windows together** — move a window against any of another window's four edges: that edge lights up in honey while they are touching. Sticking them is the **lock**: locking a window that is touching another sticks it to that edge, and unlocking it lets go. The locked one is the one that follows — a locked window cannot be dragged anyway — so dragging the unlocked one carries it along. A stuck group moves as one piece in both directions: every window in it takes the same step, and the stuck edge keeps its gap exactly. A window stuck above or below keeps its own horizontal position, one stuck to a side keeps its own baseline, and a window's link ends by itself when its partner disappears; two windows never hold each other.
- **Close (×)** and **settings (cog)** sit on every tab while the row has room for them, except that a locked window offers no cross at all: a locked window keeps exactly the tabs it has, so nothing closes in it, nothing moves out of it, and nothing new opens in it — a conversation or a console answer that would have landed there goes to another unlocked window, or to a new window of its own when every window is locked — and that window is put where it covers none of the others — candidate spots are measured as the actual drawn boxes, and a spot whose box overlaps nothing wins, the one nearest where the window would have gone; only a screen with no clear spot left accepts the least-overlapping one; when it has not, only the selected tab keeps its controls. The cross is not offered on the last tab the player could see — with one open tab, or with only tabs hidden by availability beside it — and the close itself is refused at the layout, so there is never a state with no tab; it returns as soon as another channel is open. Tab labels are shown whole while they fit; a row with more tabs than room shortens the widest labels with an ellipsis to one common width, browser-style, except that the tab in front always keeps its whole name — it is the one being read, so a crowded row shortens around it rather than hiding it — and hovering any tab names it in full beside the pointer, whatever the row had room to draw. The tabs never cross their limit — the lock, the `+` and the drag handle keep their room at the right end however many tabs there are. A crowded row gives things up in order: the labels shorten, then the unread counters go, and only when even bare tabs do not fit does the row show fewer of them — a run around the tab in front, so a tab does not come and go as the selection moves or the window is resized (one left off the row is still open and reachable by cycling). Closing removes the tab from the layout only — the channel, its history, its unread count and its mute setting are untouched, it still receives, and its messages still show in the feed unless it is muted; the channel reappears with all of it when restored, and its next message — player or system — reopens it by itself unless the channel is hidden. A reopening channel (a whisper's first message included) lands as a tab in the *active* window — the one holding the selected tab — first; a window that is locked, or whose row is **already shortening its tab names**, is passed over for the next unlocked window with whole names, and only when every window is locked or already ellipsizing does a **new window** open for the channel (placed clear of the others; at the eight-window cap a crowded row takes the tab anyway — crowded beats lost). A row that still shows every name whole always takes the tab, even when the newcomer will make it tight. A **+** control at the end of any unlocked row is the opening menu, in two sections under small headers: *Channels* lists the closed channels the player can currently see, each with its unread count (`Trade [3]`), a one-pixel upright bar in its channel colour and the channel's emoji — picking one restores it as that window's last tab and selects it, which clears the count like any tab switch — and *Direct Messages* lists every other online player under the head their whisper tab would wear, with the conversation's unread count; picking one opens (or finds) that conversation in the same window and selects it. The list follows joins and leaves while it is open, shows at most a dozen rows and scrolls by the wheel past that, a honey hairline on an edge saying more lies beyond it; a muted channel reads italic. The `+` itself carries a summed `[n]` of everything unread in the closed channels, in the tabs' honey. Muting lives in the cog menu alone. The keyboard and the middle button reach the same operations: `Ctrl+W` closes the selected tab and a middle click closes the tab under the pointer, both through the same guarded close as the cross; `Ctrl+Tab` and `Ctrl+Shift+Tab` walk every open tab across windows, and `Ctrl+Right`/`Ctrl+Left` the selected window’s, text in the field or not, while `Tab`, `Right` and `Left` on their own keep to the selected window and need an empty field — with text in it the arrows belong to the caret, as they do in any text field. The row's controls — the `+` and the close cross with their green and red hover states, the cog, the open and closed padlock with theirs, the drag handle — the emoji button, the favourite heart (plain under the pointer, filled in the palette's wine on favourited emojis and markers), and the insert-fold chevron's five animation frames with their hover states are sprites of `textures/gui/chat.png` (`ChatIconSheet`, locked to the PNG by `ChatIconSheetTest`), drawn 1:1 with the chat's shadow; the chevron plays its frames between pointing right (inserts out) and pointing left (inserts folded) on the chat's shared animation duration and easing. Everything else is mouse-driven from the row; nothing needs a command.
- **The feed** — what the closed chat shows: one stack of every unmuted channel's messages, open or closed, plus every open, unmuted whisper tab's, with no row and no bar, at a position of its own (vanilla's bottom-left by default) that is moved in the HUD placement editor independently of the windows and stored with the layout (`feed x= y=`). The windows themselves exist only while the chat screen is open.
- **Cycling** — `TAB` with an empty input, or a click on the `[Channel]` indicator, cycles through the tabs of the window the selected tab is in, never into another window. Console output arriving while the screen is open brings the Console tab to the front of its window so the player sees it — selecting it when the console shares the window the player is typing in, and only fronting the tab otherwise, so the input never jumps to another window. `/msg`, `/tell` and `/w` are the chat's own and open a whisper instead. Switching tabs is a hard cut, for the lines and for the row alike: the picked tab is forward the frame it is picked, however the pick happened.
- **Channel settings** (the cog) hold five entries, each its own thing. *Mute Channel* keeps the channel’s new lines out of the closed-chat feed — nothing else: the tab — drawn dim and italic — still shows everything when selected, its unread counters still count, and its mention cue still sounds. *Mute Mentions* silences the mention cue for the channel and nothing else: the lines still show in the feed, and mentions still count and highlight. *Hide Channel* keeps the channel closed when a message arrives: an unhidden closed channel reopens by itself with its next message — a player line, an achievement, a command’s console answer alike — exactly as a whisper does, while a hidden one stays closed, still receiving and still counting unread. All three are independent, survive closing and restoring, and travel with the layout file. *Move to its own Window* is the drag-free detach (while the window is unlocked, has another tab and the window cap is not reached), and *Close Channel* removes the tab (while it is closable), so a row too cramped to show its controls still reaches them. The menu is a plain list of entries, so further per-channel settings slot in without a new control.
- **Lock** (the padlock after the row, honey when engaged) freezes a window's layout: no reordering, undocking, docking into it, closing its tabs, or dragging it, in the chat and in the HUD placement editor alike, which shows it as `(locked)` and refuses to move it. Locking a window that is touching another also sticks it to that edge, and unlocking lets go again — see above. Selecting tabs, scrolling, muting and sending are unaffected; the grip of a locked window is inert — no hover state, no tip. The lock belongs to the window, because every movement it prevents is a movement of that window's row.

Every window draws the same way — the same bands, backdrop, heads, wrapping, entry motion and hit testing, and the same opening motion every other Lost Tales screen uses (`client.guiAnimation*`); only the input bars add their own entrance from below (`client.chatInputAnimationDurationMillis`) on top of it — inside the box `ChatWindowPlacement` gives it: the chat width at the chat scale across; the tab row, the lines it currently shows and its input bar down, newest line on the baseline; the two strips carry the window's one-pixel ivory rules on their inner rows — the tab strip's last pixel row is the top rule, the bar strip's first row the bottom one — each running the full width of the backdrop, opaque at the centre and fading to nothing at both ends, drawn last so it lies over the shades, over the tab strip and over the bar's own paint, which begins one row below the bottom rule and never darkens it. The first content pixel sits directly below the top rule; below the baseline lies the window's *trailing strip* — exactly one line of room between the newest message and the bottom rule, where the typing line lives while the view rests on the newest message. Scrolling back hands the strip to the history: the first line of scroll slides the stack down into it, so a scrolled view fills the window to the bottom rule and shows no blank line, and scrolling home gives the strip back. The message clip rounds *inward* to whole display pixels — not one display pixel of a line ever lands on a rule row, and whatever a cut gives up shows the window's own panel, drawn unclipped behind the stack — so the cut at each rule is exact and still at every frame; the tab strip's base surface is likewise drawn outside its own clip, so tabs and their shadows can never open a bright seam above the top rule. While the Lost Tales chat screen is open it draws the windows itself, after every HUD element, one complete window after another in stacking order — history, row (whose last pixel row is the top rule, so every tab and control stands on it), bar, bottom rule — so the open chat is never under the compass or a HUD panel and a front window covers the whole of one behind it; the HUD pass only cancels vanilla's chat then and draws the feed while the chat is closed. That HUD pass takes no part in depth testing and restores the state afterwards: the hotbar's item icons are drawn with depth testing on, at a raised z, and leave it on, which is why the icons alone used to show through the feed while the hotbar's flat parts stayed under it. The chat screen never dims or blurs the whole screen the way the inventory and the journal do — it is meant to read over the world — but with `client.enableChatBackgroundBlur` on (the default, needing `enableGuiBackgroundBlur`) each open window softens the world inside its own box: the frame is captured once, blurred with the same Gaussian shader the other screens use, and every window pastes its rectangle of the result under its backdrop while the rest of the screen stays sharp — and before a window that overlaps one already drawn, the frame is captured again, so the front window's blur holds the windows behind it and an overlapped window stays visible, softened, under the one in front instead of being erased by a paste of the bare world; over the history band the blur thins out to the right exactly as the backdrop does, while the tab row and the bar keep their whole band. The closed-chat feed is softened the same way while it has lines on screen: each line carries its own blur band, fading with the line and thinning to the right like its backdrop, and the capture is skipped entirely while the feed is empty. Without framebuffers or the shader everything keeps its plain backdrop. An empty channel shows one dim placeholder line, *Nothing here yet*, in place of its newest message while the screen is open. Under the control strip the history is shaded: the backdrop's plum black at half opacity along the top line, fading to nothing one line from the edge, along the bottom edge the same shade mirrored upward and reaching two lines — through the trailing strip and over the newest message — each masked by a second, horizontal fade — full at the band's left edge, nothing at its right, the two multiplied over a fine mesh — so the shade is strongest in the left corner and thins out to the right. The tab row stands on the topmost message the window currently shows, riding along as messages arrive, and on one empty line above the baseline when the channel has nothing yet, so the row is always there to drag. Each window has its own front tab, scroll position and view transition; the scroll wheel scrolls the window under the pointer (the first window elsewhere), two lines at a time — one with Shift — and the history glides to the new offset rather than jumping to it (the same `client.enableChatAnimations` switch turns the glide off with the rest of the chat's motion). A scroll offset is measured in message lines and fractions of one: the wheel moves it by whole lines, and both ends are exact rather than whole — at rest the newest message sits on the baseline, and scrolled all the way up the oldest sits on the window's top edge, however tall the window was dragged. The window's two rules are its hard edges: the message stack is clipped on them, so a line passing under one ends on the rule rather than short of it or past it, and the shades hanging from the rules fade it out before it is cut. An open window draws one backdrop panel across the whole area between its rules and lays its messages on it — a line only paints where it differs, which for now means a mention of this player tinting its own band — so nothing it does can open a seam. The closed feed keeps a band per line, since each of its lines fades on its own. The stack moves in whole display pixels, so the heads and emojis in it — pixel art sampled one texel to one pixel — stay crisp while it glides; hover cards, item tooltips, clicks and right-click copy resolve against whichever window drew the band. A window none of whose channels is currently available (a Party window outside a party) is simply not drawn until one is again.

The layout is a per-installation client preference stored in `config/losttales/chat_layout.txt` — one line per window (`window w1 locked=true x=62.50 y=8.00 lines=12 width=320 link=w2:right active=party tabs=party,faction`, where `lines` and `width` appear only for a window given a size of its own and `link` names the window it is stuck to and the side it sits on), one for the feed (`feed x=0.00 y=100.00`), one for the picker strip (`toolbar collapsed=false`), one per closed channel, one per preference (`muted`, `noping`, `hidden`) — and is never synchronized or cleared between worlds. Loading repairs whatever is stale: unknown channel ids and window ids are dropped, a channel listed twice keeps its first place, empty windows and windows past the cap are removed, percents are clamped, a window named `main` by an older layout becomes an ordinary window, and any channel that is neither placed nor listed as closed is appended to the first window, so a channel added in a later version is never silently lost. A file with no usable window gets one window holding every open channel; with everything closed, the default layout.

## Emojis

Player channel messages may contain emoji shortcodes such as `:smile:`. With `client.convertChatEmoticons` on (the default), classic emoticons typed as whole words — `:)` `:(` `:D` `:P` `xD` `:O` `<3` `</3` `:*` `D:` `:'(` `:')` and their nosed forms — become their canonical shortcodes once, as the message goes out, so every recipient sees the same thing whatever their own settings; nothing inside a share token or a command is touched, and a conversion that would push the message over the limit sends the text as typed instead. Discord-recognised alias names (`:flushed_face:`, `:satisfied:`) complete and normalize to their canonical shortcode on input; the wire, copies, and the renderer only ever carry canonical names. They travel as ordinary message text — the server, the packets, and copied messages always carry the canonical `:name:` form — and each receiving client with `client.enableChatEmojis` enabled renders recognized shortcodes as inline 10×10 sprites that participate in normal layout and line wrapping. Unknown, incomplete, or malformed values (`:does_not_exist:`, `:sm`, a lone `:`) stay literal text, so mixed setups degrade to readable shortcodes. Disabling the toggle also shows shortcodes as plain text.

In the input field a complete shortcode of a registered emoji is shown as the sprite it will be in chat, exactly like a resolved share token: the raw `:name:` stays what goes on the wire, but it edits as one character — the caret stands on either side and never inside, Left and Right step across it whole, Backspace behind it and Delete before it remove all of it, and a click lands on its nearer edge. An alias or an unfinished name stays literal text, and commands never preview. The field's horizontal scroll follows what is drawn, not the raw text: vanilla scrolls by raw character widths, but a token draws as one narrow element (`:creeper:` measures nine characters and draws ten pixels), so the offset is recomputed from the drawn widths every frame — zero while everything fits the box, always on a token boundary, keeping the caret visible with no empty tail — and a field full of emojis holds as many as its pixels do before it scrolls at all. Completing a shortcode — from the list, or by typing its closing colon — puts the same single space behind it every inserted token gets, so the next word stands apart from the emoji however it was put there. A small smiley button on the input bar, beside the send arrow, toggles the emoji picker; selecting an emoji inserts its shortcode at the current cursor position without disturbing the rest of the input, and the panel stays open for further picks. The picker has a search field that filters by name, a Favorites row (right-click any cell to toggle a favorite, marked with a small gold dot), a Frequently Used row ranked by how often each emoji has been sent, and the full grid; hovering a cell shows its shortcode as a tooltip. Favorites and usage counts are per-installation client preferences stored in `config/losttales/chat_emojis.txt` — nothing is synchronized. The button and panels are positioned from the live chat geometry, so GUI scale and resolution changes are handled.

Typing an unclosed shortcode such as `:fl` shows a completion list above the input, filtered live as more characters are typed. Click a row or use Up/Down plus Tab or Enter to complete it (Enter never sends the message while the list is open); Escape hides the list without closing chat. Completions never anchor on the closing colon of an already-completed emoji, and commands never trigger the list.

The canonical registry is the `ChatEmoji` enum (`chat/emoji/`), which doubles as the picker order: constants are declared thematically the way Discord browses — the smileys in Unicode's expression sequence (happy through affectionate, silly, neutral, sick, surprised, sad, angry), then the monsters, hands, hearts, animals, food, and the mod's own objects — while each constant's sheet cell is pinned explicitly, so reordering the browsing order can never remap artwork. Adding an emoji means drawing it into a free 10×10 cell of `textures/gui/emojis.png` (11-pixel stride, 1-pixel gutters) and adding one enum constant naming that cell, in the thematic place it reads best; `ChatEmojiSheetTest` fails the build if the sheet and registry disagree. Shortcodes are lowercase `a–z`, `0–9`, `_` and are wire format: never rename or reuse one. `ChatEmoji` and the parser are deliberately free of client classes; sprites, markers, the picker, and rendering live in client-only code.

Every chat element shares one shadow rule: text, emojis, head icons, item icons and marker glyphs draw a flat `#2d1e2f` silhouette at half the content's opacity, offset one pixel down-right under it. Sprites get that through `LostTalesSilhouetteRenderState`, which swaps the texture environment so a textured quad takes its colour from one constant and only its alpha from the texture; a tinted copy of the sprite would keep its own dark outline and go black instead.

Inline glyphs — emojis, item icons, map-marker glyphs, and the quest glyph on the toolbar — follow one set of rules in `ChatInlineIcons`, in the message lines, the pickers, the completion lists and the toolbar buttons alike: a glyph occupies the ten-pixel slot its two bold spaces reserve and fills a ten-pixel content box centred in it, two rows above the text's top edge so it is centred in the eleven-pixel band. An emoji is drawn 1:1, an item's sixteen-pixel sprite is scaled onto the box, and a marker's opaque artwork (using the art bounds the marker atlas already records, not its padded seventeen-pixel cell) is fitted into it by its larger edge — always uniformly, never stretched — so every kind reads at the same apparent size with the same baseline, spacing and shadow. Every glyph fades with its line: the line's resolved alpha is handed down unchanged, and for items — whose vanilla renderer resets the vertex colour to full alpha in every branch — it is applied through the texture environment (`LostTalesSilhouetteRenderState`, the same mechanism the flat shadows use), while blocks vanilla draws as cubes are posed as vanilla poses them but drawn with blending on, since vanilla's cube branch also turns blending off and would pop the cube out at half fade. A fading enchanted item loses its glint for the fade (the glint is additive on the inverse of its texture's alpha and would brighten instead). A marker glyph keeps exactly the colour the marker has on the map — plain white stays white, the sprite's own pixels untinted — while the bracketed name beside it reads in the marker's text colour, plain white swapped for the chat's ivory so the name shares the one white every other word uses. On the toolbar buttons every glyph fills the same ten-pixel box centred in the twelve-pixel button, fitted by its larger edge exactly as it is inline — the emoji 1:1, the sword's sprite scaled onto the box, the point-of-interest and quest marker glyphs fitted uniformly — so the emoji, item, marker and quest buttons read at one size on one baseline with one hitbox, and nothing is stretched.

## Sharing items and locations

A player can share an item from their own inventory or a map marker inline. The insert buttons sit on the input bar between the emoji button and the character counter, folded away leftward by a small chevron beside the emoji button (the fold is remembered with the layout); expanded they run, right to left: the sword button, which opens an item picker (search field plus collapsible Hotbar, Inventory and Armour sections), the marker button, which opens a picker of every map marker the map would show, and the quest button. Only places the player has actually reached are offered: a marker must be discovered (if it is discoverable) and its fast-travel region unlocked, and the server applies the same rule on send, so an undiscovered question mark cannot be shared. The marker picker opens with a **Favourites** section (right-click a row to toggle, marked with the same gold dot as the emoji picker) and a **Recently Travelled To** section (the last eight destinations the player actually arrived at, most recent first — reported by the server from LOTR's own fast-travel completion through `LostTalesFastTravelArrivalPacket`, so a refused or cancelled travel never counts), followed by one collapsible section per marker type — the glyph the marker is drawn with, which is the taxonomy the marker atlas already defines: Settlements, Graveyards, Forests, Mountains, Ports, Harbours, Bridges, Camps, Waypoints, Points of Interest, Quests and so on — instead of one generic "Point of Interest" list. Sections with nothing in them are not shown — in every picker, so an empty hotbar or inventory section simply does not appear — and a search shows one flat result list. No picker grows past the middle of the screen: a longer list scrolls inside the panel with the mouse wheel — the rows gliding to the new offset with the same eased motion the history scrolls with, instantly with chat animations off — clipped below the search row, with a thin track at the right edge. Favourites and recent destinations are per-installation client preferences stored in `config/losttales/map_markers.txt`, keyed by marker id; an id that names no visible marker on the current server is kept but not shown. The quest button opens the quest picker on the same frame; quest entries are not shareable yet, so it shows an empty-state line, and quest entries will slot into that picker without another redesign. Typing `[i:` or `[m:` instead shows a completion list (icons and names; duplicates are numbered `Name (2)`). Either inserts a token such as `[i:Iron Sword]`, `[i:Iron Sword#2]` for the second stack of that name, or `[m:Northgate Test City]`. A token the client can already resolve is shown in the input field as the preview it will be in chat — the bracket, the icon, the real name in the rarity's or marker's colour — while the raw text underneath stays exactly what goes on the wire: the caret walks through it character by character, a click lands on the token's nearer edge, and an unresolvable token stays literal text. A shared marker renders as its glyph in the chat's ivory plus its name in the marker colour; hovering shows its coordinates and clicking opens the LOTR map and flies the camera to it (with the selection frame when the marker is known locally). A message holds as many shared things as it has room for, wrapping over as many lines as that takes; a token counts as a single character against the visible-character limit, which the field enforces. The ceilings are defensive ones, taken from what the wire carries rather than from the interface. The count, `ChatShareTokenParser.MAX_TOKENS` (32), bounds the collections behind a message and keeps the *request* — a slot index or a marker id per token — near seventeen kilobytes, inside the 32767 bytes a client-to-server custom payload may carry at all. What the *delivered* line costs is bounded by bytes instead, `ChatShowcase.MAX_TOTAL_BYTES` (8 KiB for the whole set), because a marker costs a fraction of what an enchanted stack does: a message of markers carries the full count, and a message of full stacks stops attaching once the set reaches the budget — the rest stay the text they were typed as, and the sender is told once. Both bounds are asserted against the real codecs in `LostTalesChatPacketTest`. Reaching the ceiling is a wall the field enforces like the character limit: a pick beyond it is refused with a notice instead of inserted, since the server would deliver it as dead literal text. When the message is sent, the client resolves each token to a reference — a slot index for an item, a marker id for a marker — and sends only that alongside the text; the server re-reads the slot from the sender's live inventory or the marker record from world data under the sender's own visibility rules, checks that the real name matches the token, and attaches a validated payload (a stack bounded to 1 KiB of compressed NBT, or the marker's public id, name, icon, colour, dimension and coordinates) to the message it distributes. Recipients render a validated token as a small icon plus the bracketed name in its rarity colour, with the item's normal tooltip (name, enchantments, lore, attributes, durability, mod tooltip lines) on hover; the stack is decoded once on arrival. A token the server could not verify — the item was moved or dropped before sending, the name no longer matches, a forged slot, or an over-sized stack — is delivered as the literal text the sender typed, and the sender is told once per message. Showcase tokens, like emojis, are plain message text on the wire and in copied history.
