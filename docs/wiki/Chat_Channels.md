# Chat channels

Lost Tales provides five player-conversation channels, a staff channel and a private console, while leaving commands, server messages, and other mods' chat components on Minecraft's normal paths; it only decides which tab such a line is filed under.

Channels are presented — tabs, the `[Channel]` indicator, and `TAB` cycling — in this order:

- **Global** (channel id `all`) is global in-character conversation.
- **Proximity** is in-character conversation delivered only to players in the sender's dimension and within the server's configured radius.
- **Faction** is in-character conversation delivered only to online characters whose configured faction matches the sender's active character. It is unavailable without a valid active-character faction.
- **OOC** is global out-of-character conversation and uses the Minecraft account name and account skin.
- **Party** is in-character conversation delivered only to online members of the sender's current Lost Tales party. It is unavailable without a valid party.
- **Operator** (channel id `admin`) is a staff channel: only server operators (permission level 2) can read it or talk in it, with their account identity. The tab appears only once the server has told the client the player is an operator (`LostTalesChatAccessPacket`, sent on login and whenever a staff message is refused), and the server checks operator status again on every send, so a client cannot claim the tab for itself.
- **Whispers** are private conversations between two accounts. `/msg`, `/tell` or `/w <player> [message]` — or clicking a sender's name or head in any line — opens a tab named after that player in the window you are typing in and selects it; text after the name is sent straight away. A whisper tab works like any other tab (drag, dock, detach, mute, close) and shows the sender's account identity; the first message from someone opens their tab on your side too, with a ping. The server delivers a whisper only to the sender and that one online player, each told who the other party is, and refuses an unknown name with a notice; closing a whisper tab just hides the conversation until the next message. Conversations end with the session: whisper and NPC tabs are closed when the history goes (leaving a server) and are never written to the layout file. LOTR NPC speech (`LOTRSpeech.sendSpeech` goes to one player) appears as a whisper from the NPC, in a tab bearing its name and kept apart from a player of the same name (`npc:Name`); replying there sends nothing — nobody is on the other end — but the line is shown as a whisper of yours, for the fun of it.
- **Console** is the player's private console: what only this player sees — command output, fast-travel countdowns and timers, game-mode confirmations, whispers, LOTR notices, other mods' lines — lands in this tab only, keeping the conversation tabs clean. It takes commands only: plain text typed with the console selected is refused with a notice instead of being sent. It is always available and needs no character. Lines the whole server sees — vanilla and Middle-earth achievements, death messages, joins and leaves, `/say` and `/me` — are filed under **Global** instead, because they are conversation everyone shares.

Where a vanilla or LOTR line goes is decided by `ChatSystemLineClassifier` from the translation key the server built the component with (`chat.type.achievement`, LOTR's `chat.lotr.achievement`, `death.*`, `multiplayer.player.joined`, `chat.type.announcement`, …), never from its rendered text, so it does not depend on the client's language. Every incoming line is printed from the `ClientChatReceivedEvent` handler (at the lowest priority, after every other mod has seen the event) with a tracked line id, its channel prefix and a timestamp — `Console: [18:45] Your game mode has been updated`, `Global: [18:45] Player has just earned …` — so the feed names the channel and the tabs file it like any other line; the server's component itself is untouched. Adding a category means adding a key to the classifier, nowhere else. Lines printed directly on the client without passing through the event (a HUD toggle notice) stay untracked and show in the console without a prefix.

The presentation order is `ChatChannel.presentationOrder()`; the enum's declaration order is left alone because client view state is indexed by ordinal, and channel ids on the wire are strings.

In-character messages require an active role-playing character and snapshot its name and skin when the server accepts the message, so existing history does not change after a character switch. The current LOTR title and the exact color exposed by LOTR's faction explorer are snapshotted presentation details. Players without an active character can use OOC with their account identity and skin, but cannot send to Global or another in-character channel.

LOTR NPC speech that would print as a plain yellow chat line is restyled on the client into the same presentation: LOTR sends speech to one player, so an NPC message is a whisper from the NPC — a tab named after it — with a timestamp, the NPC's rendered skin as its head icon, and a honey-coloured name. This is purely visual — a coremod hook replaces only the final chat print in LOTR's speech packet handler, so speech content, recipients, NPC behaviour, and LOTR's immersive floating speech are untouched, and any failure falls back to LOTR's original line. It can be disabled with `client.enableNpcChatStyling`.

Chat lines are spaced eleven pixels apart (vanilla uses nine), each line's backdrop filling the full stride so neighbouring bands connect seamlessly; the extra height is what gives inline emotes and head icons their room. Channel colours come from the shared palette — Global is meadow green, Proximity teal, Party seafoam, OOC orchid — except Faction, which shows the sender's exact LOTR faction colour; the `:` after the channel name and the channel indicator share the channel's colour, and timestamps use the palette's sand (`#dbc9b4`) in italics. Clicking a message's head icon opens a whisper with the sender, exactly as clicking the name does.

Players can style their own messages with `&`-formatting codes (`&6gold`, `&lbold`, `&r` reset — the usual Minecraft codes with `&` in place of the untypable section sign). Translation happens on the receiving client at display time; the wire format, copied text, and history keep the ampersand form. Mentioning someone with `@Name` — their account name or active character name, case-insensitive with word boundaries — highlights the message's backdrop in the palette's wine for the mentioned player and plays a ping sound on arrival (`client.chatPingSound`, the note-block pling `note.pling` by default; self-pings work). The cue is played as a non-positional UI sound on the mentioned client only: the server never triggers it and no other client hears it. Config files written by the first backport still carried LOTR's horn (`lotr:item.horn`) as the value; that legacy value is migrated back to the pling on load.

A message longer than the chat width wraps under its sender rather than back to the left edge:

```text
[12:34] <Aragorn> This is a long roleplaying message that
        continues here under the opening bracket instead
        of returning to the far left side.
```

The layout is a proper model, not a post-hoc offset. Every Lost Tales line carries a zero-width anchor marker after its header (channel prefix and timestamp), in front of the sender's opening bracket; the coremod hooks the seam inside `GuiNewChat.func_146237_a` where vanilla has finished wrapping and is about to file lines into the history, and `ChatLineWrapper` lays the message out instead: it measures the header with the same formatting-aware width the renderer draws with (so `&`-codes cost nothing), breaks the text at spaces (dropping the break space, carrying active formatting codes onto the next piece, treating the head, emotes and showcase icons as atomic words, and cutting a word longer than a whole line so any input makes progress), and opens each continuation line with an indent marker recording the header width twice — with the channel prefix shown (closed HUD) and hidden (open screen) — so lines sit under the bracket in both states. With timestamps off and the screen open there is no header, and continuation lines start at the left edge under the bracket. The renderer and every hit test advance the cursor by that marker, so clicks, hovers and the copy action on a wrapped line land where the line is drawn. Vanilla keeps the history, scroll, trimming and resize bookkeeping, and re-runs the layout from the original message whenever the chat width or GUI scale changes. A header so long it would leave no real room starts the text a line down with the indent capped at half the width; a header wider than the chat falls back to vanilla's wrapping. Without the coremod patch the markers are inert and lines wrap as vanilla wraps them. Minecraft's "chat colours" option is honoured: switched off, every formatting code — the channel and name colours as much as a sender's `&`-codes — is stripped before measuring and drawing and the whole line is plain ivory, exactly as vanilla renders colourless chat; the layout measures the same stripped text so wrapping and drawing always agree.

Enter sends the message and keeps the screen open with an empty field for the next one (vanilla closed it); only Escape, or the player closing the chat, swaps back to the feed. Text typed into the input is not lost when the screen is closed or resized: the unsent draft is kept (per session, cleared on disconnect) and restored the next time the chat opens, unless the screen was opened with its own default text such as `/`; sending a message or command spends the draft. Drafts belong to the tab they were typed in: switching tabs or windows puts the field's text away with the tab just left and brings back whatever the tab coming to the front had unsent, so a half-written whisper does not follow you into Global. Typing `@` shows a completion list of online players (yourself first, then alphabetical), filtered live and accepted by click, Up/Down, Tab, or Enter, exactly like the emote completions. Each online player appears once: in OOC the list shows and inserts the Minecraft account name, in role-play channels the active character name, but typing either name finds the player (`@Steve` and `@Aragorn` both offer `Steve123` in OOC and `Aragorn` in Global). The pairing of account and character comes from the public appearance sync the server already sends for every online player (it now carries the account name), so the list never guesses from display names. Mention detection is purely client-side presentation (each client checks its own names), and `client.enableChatPings` turns the whole feature off. While the field holds a message (not a command), the client tells the server every 2.5 seconds that it is typing into the selected tab, and once that it has stopped when the field empties, the tab changes, the message goes out or the screen closes; the server relays the presence — the name the message would show, never any text — to exactly the players who would receive a message sent there now, under the same checks, and to nobody for a command, an NPC conversation or a channel the player cannot send to. Each window shows *Name is typing…*, two or three names, or *N people are typing…* above its bar for its front tab; a name not refreshed for six seconds drops out on its own, so a lost stop never leaves a ghost. `client.sendChatTypingStatus` and `client.showChatTypingIndicators` switch each side off for this player; `chat.typingIndicators` switches the relay off for the whole server.

With the chat screen open a message reads `[HH:mm] <HEAD CharacterName, the Faction Title> Message`; with it closed the HUD shows every channel in one feed and prefixes each line with its channel, `Global: [HH:mm] <HEAD CharacterName, the Faction Title> Message`. A titled sender is named the way LOTR names its NPCs (`entity.lotr.generic.entityName`, `%s, the %s`): the character name, then `, the ` and an epithet made of the sender's LOTR faction name and LOTR title — `Aldric, the Gondor Farmer`, or `Aldric, the Farmer` when the faction is unknown. The server sends the title and the faction name separately (the faction name is appended after the original wire layout); the receiving client composes them through `chat.losttales.title.epithet` (`%s %s`) and `chat.losttales.title.suffix` (`, the %s`), so the wording is localizable, and marks the suffix with a title marker carrying its colour and the bare epithet. A sender without a title is shown exactly as before — no comma, no "the", no faction. On account lines — OOC, Operator, Console and whispers, where the sender is the Minecraft account rather than a character — a server operator's line opens with `[Operator]` in the palette's crimson ahead of the name (`chat.losttales.tag.operator`); the server sets the flag when it builds the line, so the client never decides who is staff, and role-play lines never carry it. Titles appear only where Lost Tales draws its own chat lines and their hover card; vanilla and third-party name rendering is untouched. The prefix is built once and skipped at draw time while the tabs already separate channels. Channel names use normal title casing, and Faction uses the active faction's exact color. The invisible head marker reserves exactly the icon width; there is no extra visible padding inside the brackets, and both brackets use the character name's exact RGB color. Clicking the displayed name opens (and selects) a whisper tab with that account, including for character channels where the visible role-play name differs from the Minecraft account name. While chat is open, hovering the rendered head or name shows a bounded player card. Its first line is `Character Name (Account Name)` for a character identity and just `Account Name` for an account identity (OOC lines, players without a character) — never empty parentheses. Below it, each of race, faction (the character's selected starting faction, never alignment or reputation), level, gender, age, and the biography is shown only when known, the biography wrapped to the card and bounded to a few lines. The details come from the public active-character appearance the server synchronizes for every online player — the appearance sync now carries starting faction, level, age, and description alongside name, race, gender, skin and capes, all appended after the original wire layout — and are shown only when they describe the character the line names, so a historic line never borrows a later character's details.

While the chat screen is open, a row of folder-style tabs stands on top of the topmost visible message (on the baseline when the view is empty), riding along with the stack as messages arrive and as the history enters — one per channel that is open in that window and currently available to the player. The tabs stand side by side with a one-pixel seam, like a browser's; the selected tab comes forward, lifts slightly, and runs into the box, and each tab's top edge carries its channel's colour, full at the centre and fading out to both ends. Every tab wears an icon before its name (`ChatChannelIcons`): an emote per channel — Global smiles, OOC is silly, Party is joy, and so on — and a head for conversations: the partner's own head for a whisper with a player the client can place (in the world or in the appearance sync), the NPC's portrait for an NPC conversation, remembered from its speech for the session; a whisper whose partner is not placeable yet wears the shy emote, an NPC whose portrait has not been seen the grin. The icon is drawn at the sprite's own size, centred in a resting tab's interior with a clear row above and below it, the label and controls centred with it; the selected tab's lift carries all of it up rather than re-centring it. A decoration only. Clicking a tab selects it; with an empty input, `TAB` (or clicking the `[Channel]` indicator beside the input) cycles the open channels in window and tab order. With text or a command present, Minecraft's normal autocomplete remains active. The selected channel decides both which history is shown and where a new message is sent: each tab shows only its own channel's messages (untracked vanilla lines ride with the Console tab wherever it lives) and keeps its own scroll position, which survives closing and reopening the screen. A window — its history, backdrop, tabs and input bar — is one motion group: opening the screen brings it in with the same sampler, easing, direction and duration every other Lost Tales screen uses (`client.guiAnimation*`), the tabs and bar taking their position from the bands the history drew and their opacity and motion from the same sample, so they enter, settle and fade together; the bands are recorded from the first frame of the fade, while the lines are still too faint to paint, so the tabs are there from the start rather than popping in once the lines become visible. A tab that received messages while another tab was selected shows textual counters after its name: `Gondor [2] [5]`, where the first, salmon-coloured `[p]` is the number of unread messages that mentioned you and the second, honey-coloured `[x]` the number of other unread messages; a message is counted once, as a ping or as unread, never both. A counter appears only while its count is positive (`Party [3]` with no pings), caps at `[99+]`, updates as messages arrive, and clears once the tab is viewed. The counts live in `ClientChatChannelViews`, the single source of unread state; a closed channel keeps counting, and the `+` menu shows the same count beside its name (`Trade [3]`). With the chat screen closed the windows are not drawn at all; one *feed* shows every unmuted channel's messages, whether or not the channel has a tab (with their channel prefixes), as a single fading stack at its own position, so nothing is missed. Messages are never copied; the views are filtered indexes over vanilla's own history, described by a `ChatLineFilter` (a set of channels, with the console's untracked lines) and cached per filter. That history keeps `client.chatHistoryLines` messages (1000 by default, 100–5000) rather than vanilla's hundred: the coremod replaces the literal in `GuiNewChat`'s own trimming with the configured capacity, so a long session stays scrollable in every tab; the history still belongs to vanilla and goes with the world on disconnect. Without an active character the Global tab stays readable (achievements and other vanilla lines live there) but only OOC accepts messages — the indicator shows a read-only channel muted and Enter shows a notice instead of sending; Party and Faction are omitted when the active character cannot use them. The tab row only appears once the open view has at least one line; Tab and the indicator still switch channels before that. Hovering a row of the mention completion list shows the same player card as hovering a name in chat. The Faction tab, indicator, and message prefix show the active character's LOTR faction name (for example `Gondor`) rather than the word "Faction"; the logical channel and its routing are unchanged, and the catalogue name is used if LOTR cannot resolve the faction. Right-clicking a visible message copies only its message body and briefly confirms the action. Chat and the other Minecraft GUI screens use the same Lost Tales cursor as the LOTR map.

Every overlay the screen draws — tabs, the channel indicator, the emote, item, marker and quest buttons, the completion lists, the pickers — registers the rectangle it actually painted for that frame (in screen space, whichever motion group drew it), and hover, tooltip, and click handling check that record before touching the message stack. While the pointer is inside an overlay, the lines underneath are neither hovered nor clickable, so no hover card, item tooltip, or link click can fire through a popup; because the record comes from the draw itself, visual and interaction order cannot disagree. Chat lines are hit-tested the same way: the draw pass records the exact screen band of every line it draws (scroll, chat scale, view filtering, and entry motion included), and the hover card, component tooltips, clicks, and right-click copy resolve against those bands.

`chat.proximityRadius` is a server-authoritative gameplay setting. Timestamp visibility, the emote toggle, and the message, input-bar and selector animation settings are client presentation preferences under the `client` category. A new message eases upward and slides in from the left with a short fade, briefly overshooting its resting position to the right before settling. Vanilla's chat hit test (`GuiNewChat.func_146236_a`) is routed through the drawn bands by the coremod while the Lost Tales chat screen is open, so LOTR's achievement hover card and any other mod asking vanilla where the pointer is get the same answer as Lost Tales itself, and get nothing under a popup. Disabling animation does not alter layout, routing, history, or command behavior. Chat surfaces — the message backdrop and the input bar included — use the palette's plum black (`#2d1e2f`) at half opacity; the message backdrop fades to transparent over its final third, while the input bar is solid across its width. Each window has its own input bar one chat line below its newest line, as tall as the control strip and exactly as wide as the window (the chat width setting at the chat scale, fade disregarded); a send arrow sits at its right end, so Enter is not the only way to send, and the emote, item, marker and quest buttons stand in a small tab strip of their own — one chat line tall — on the bar's top edge above that end, their pickers opening above it. A chevron on the strip's right-hand corner folds the buttons down into the bar, leaving only a low handle to unfold them; the choice is kept in the layout file (`toolbar collapsed=`). Left of the send arrow a small `37/100` counter, drawn at three-quarter size in the timestamp's sand, counts the message's visible characters; the field refuses input past the limit (a paste is trimmed back to it), and the counter turns salmon when it is reached. The bar of the window holding the selected channel carries the indicator, the text field and the toolbar; the other windows show their bar with the name of their front tab dimmed — followed by that tab's unsent text, if it has any, so a draft stays in view where it was typed — and a click in it moves the input there.

## Chat windows, tabs and layout

The tabs are not fixed. The layout is one model, `ChatWindowLayout`: a list of windows, each an ordered row of channel tabs with a front tab, a lock and a position, plus the set of muted channels. Every window is equal. The default layout is two of them: a console window (Console, Operator) in the top-left corner and a conversation window with every other channel in the bottom-left corner. A window that loses its last tab disappears, and the last open tab of all can never be closed, so there is always somewhere to type. A channel lives in at most one window, and a channel in no window is *closed*: its tab is gone, but it keeps receiving, keeps its history, unread count and mute setting, and stays in the feed unless muted. The in-game chat screen, the closed-chat overlay and the HUD placement editor all read and write this same model, so a window moved in one place is exactly where the others find it.

- **Reorder** — drag a tab along its row. **Detach** — drag it clear of the row (about fourteen pixels above or below it) and release: the channel becomes a window of its own, its row landing under the pointer. **Dock** — drag a tab onto another window's row; a honey insertion mark shows where it will land. A press that moves less than four pixels is a click and just selects the tab; Escape cancels a drag. A window whose only tab is dragged out simply moves; a window whose last tab is docked elsewhere or closed disappears (the last open tab of all cannot be closed). There are at most eight windows.
- **Move a window** — drag it by the dotted grip at the right end of its strip, by the empty strip, or by its messages (a press that does not travel four pixels stays the click it always was: links, names, right-click copy); the row, the lines and the bar move as one piece: the row and bar are drawn on the same fractional position the lines are. The drag follows the raw mouse in fractional pixels, so it glides rather than stepping by whole GUI pixels. A window is anchored by its baseline — the edge its newest message sits on — with messages growing upward and its input bar hanging below, so it never moves when a message arrives; the box is only as tall as what the window currently shows, so a window with a few lines can be placed anywhere, the top edge of the screen included A window parked high that later fills up is pushed down just far enough to keep its top on screen — it grows downward from there — and returns to its anchor as its lines go; the stored position never changes. Windows keep off the screen edges only — the same four-pixel margin every HUD panel keeps — and may overlap one another, in the chat and in the HUD placement editor alike: the window in use (the one holding the selected tab, or the one last dragged) is drawn in front and is the one the pointer reaches first; a growing window never loses lines to a neighbour. Only a window *linked* above it moves up with it, until that one meets the top of the screen. The stack's rise on a new message plays only while the window is still growing. A window none of whose channels the player can currently see (a Party window outside a party) is not drawn, does not appear in the HUD placement editor, and stands in nothing's way. It is all recomputed every frame from the stored anchors and undoes itself as lines go.
- **Linking** — drag a window to within a few pixels of another window's top or bottom edge: the edge lights up in honey, the window snaps a margin away from it, and releasing links the two. A linked window keeps that gap from then on — when the other grows, shrinks or moves, it follows — while its own horizontal position stays its own. Dragging the linked window away (in the chat or in the HUD placement editor) breaks the link; a window's link also ends when its partner disappears, and two windows never hold each other. Links are stored with the layout (`link=w2:above`). The position is stored as a percentage of the baseline's travel, so it survives resolution and GUI-scale changes and is clamped inside the screen like every other HUD panel.
- **Close (×)** and **settings (cog)** sit on every tab while the row has room for them, locked window or not (the lock guards movement); when it has not, only the selected tab keeps its controls. The cross is not offered on the last tab the player could see — with one open tab, or with only tabs hidden by availability beside it — and the close itself is refused at the layout, so there is never a state with no tab; it returns as soon as another channel is open. Tab labels are shown whole while they fit; a row with more tabs than room shortens the widest labels with an ellipsis to one common width, browser-style, and the tabs never cross their limit — the lock, the `+` and the drag handle keep their room at the right end however many tabs there are (a tab that finds no room at all is left off the row, still open and reachable by cycling). Closing removes the tab from the layout only — the channel, its history, its unread count and its mute setting are untouched, it still receives, and its messages still show in the feed unless it is muted; the channel reappears with all of it when restored. A **+** control at the end of any unlocked row lists the closed channels the player can currently see, each with its unread count (`Trade [3]`) and a one-pixel upright bar in its channel colour before the name; picking one restores it as that window's last tab and selects it, which clears the count like any tab switch; each row also shows the channel's emote. The `+` itself carries a summed `[n]` of everything unread in the closed channels, in the tabs' honey, and each row of its menu has a second column — *Mute* or *Unmute* — that quiets or restores the channel's notifications without restoring the tab and keeps the menu open; a muted closed channel reads italic there. The keyboard and the middle button reach the same operations: `Ctrl+W` closes the selected tab and a middle click closes the tab under the pointer, both through the same guarded close as the cross; `Ctrl+Tab` and `Ctrl+Shift+Tab` walk every open tab across windows, text in the field or not, while `Tab` alone keeps to the selected window and needs an empty field. The row's controls — the `+` and the close cross with their green and red hover states, the cog, the open and closed padlock with theirs, the drag handle — and the emote button are sprites of `textures/gui/chat.png` (`ChatIconSheet`, locked to the PNG by `ChatIconSheetTest`), drawn 1:1 with the chat's shadow. Everything else is mouse-driven from the row; nothing needs a command.
- **The feed** — what the closed chat shows: one stack of every unmuted channel's messages, open or closed, plus every open, unmuted whisper tab's, with no row and no bar, at a position of its own (vanilla's bottom-left by default) that is moved in the HUD placement editor independently of the windows and stored with the layout (`feed x= y=`). The windows themselves exist only while the chat screen is open.
- **Cycling** — `TAB` with an empty input, or a click on the `[Channel]` indicator, cycles through the tabs of the window the selected tab is in, never into another window. Console output arriving while the screen is open brings the Console tab to the front of its window so the player sees it — selecting it when the console shares the window the player is typing in, and only fronting the tab otherwise, so the input never jumps to another window. `/msg`, `/tell` and `/w` are the chat's own and open a whisper instead. Switching tabs is a hard cut for the lines; only the tabs themselves ease.
- **Mute** (in the cog menu) is a notification preference, not deletion: a muted channel's lines are left out of the closed-chat overlay and its mention cue does not sound, but its tab — drawn dim and italic — still shows everything when selected, and its unread counters still count. Mute and close are independent: closing a tab does not mute the channel, muting does not close its tab, and a closed channel keeps its mute setting for its return. The cog menu also offers the two halves of a mute on their own: *Hide from feed* keeps the channel's lines out of the closed-chat feed while its mention cue still sounds, and *Silence mentions* stops the cue while the lines still show; each is its own preference, stored with the layout (`nofeed`, `noping`), untouched by muting or unmuting, and kept while the tab is closed. Both the cog menu and the `+` menu open upward from the strip, so they never lie over the history they belong to, and are outlined as panels. The menu also offers *Move to its own window* (the drag-free detach, while the window is unlocked, has another tab and the window cap is not reached) and *Close channel* (while the tab is closable), so a row too cramped to show its controls still reaches them. The menu is a plain list of entries, so further per-channel settings slot in without a new control.
- **Lock** (the padlock after the row, honey when engaged) freezes a window's layout: no reordering, undocking, docking into it, closing its tabs, or dragging it, in the chat and in the HUD placement editor alike, which shows it as `(locked)` and refuses to move it. Selecting tabs, scrolling, muting and sending are unaffected; the grip of a locked window is inert — no hover state, no tip. The lock belongs to the window, because every movement it prevents is a movement of that window's row.

Every window draws the same way — the same bands, backdrop, heads, wrapping, entry motion, scroll bar and hit testing, and the same opening motion every other Lost Tales screen uses (`client.guiAnimation*`); only the input bars add their own entrance from below (`client.chatInputAnimationDurationMillis`) on top of it — inside the box `ChatWindowPlacement` gives it: the chat width at the chat scale across; the tab row, the lines it currently shows and its input bar down, newest line on the baseline, with a third of a line of backdrop padding above the topmost line and below the newest so the text touches neither the tab row nor the window's bottom edge; directly under that bottom padding, and directly above the top padding, a one-pixel ivory rule runs the full width of the backdrop, opaque at the centre and fading to nothing at both ends, drawn last so it lies over the shades and over the tab strip. While the Lost Tales chat screen is open it draws the windows itself, after every HUD element, one complete window after another in stacking order — history, row (whose last pixel row is the top rule, so every tab and control stands on it), bar, bottom rule — so the open chat is never under the compass or a HUD panel and a front window covers the whole of one behind it; the HUD pass only cancels vanilla's chat then and draws the feed while the chat is closed. An empty channel shows one dim placeholder line, *Nothing here yet*, in place of its newest message while the screen is open. Under the control strip the history is shaded: the backdrop's plum black at a third opacity along the top line, fading to nothing over half a line from the edge — the padding moves where the shade starts, never how far it reaches — along the bottom edge the same shade mirrored upward, each masked by a second, horizontal fade — full at the band's left edge, nothing at its right, the two multiplied over a fine mesh — so the shade is strongest in the left corner and thins out to the right. The tab row stands on the topmost message the window currently shows, riding along as messages arrive, and on one empty line above the baseline when the channel has nothing yet, so the row is always there to drag. Each window has its own front tab, scroll position and view transition; the scroll wheel scrolls the window under the pointer (the first window elsewhere); hover cards, item tooltips, clicks and right-click copy resolve against whichever window drew the band. A window none of whose channels is currently available (a Party window outside a party) is simply not drawn until one is again.

The layout is a per-installation client preference stored in `config/losttales/chat_layout.txt` — one line per window (`window w1 locked=true x=62.50 y=8.00 active=party tabs=party,faction`), one for the feed (`feed x=0.00 y=100.00`), one for the picker strip (`toolbar collapsed=false`), one per closed channel, one per notification preference (`muted`, `nofeed`, `noping`) — and is never synchronized or cleared between worlds. Loading repairs whatever is stale: unknown channel ids and window ids are dropped, a channel listed twice keeps its first place, empty windows and windows past the cap are removed, percents are clamped, a window named `main` by an older layout becomes an ordinary window, and any channel that is neither placed nor listed as closed is appended to the first window, so a channel added in a later version is never silently lost. A file with no usable window gets one window holding every open channel; with everything closed, the default layout.

## Emotes

Player channel messages may contain emote shortcodes such as `:smile:`. They travel as ordinary message text — the server, the packets, and copied messages always carry the canonical `:name:` form — and each receiving client with `client.enableChatEmojis` enabled renders recognized shortcodes as inline 10×10 sprites that participate in normal layout and line wrapping. Unknown, incomplete, or malformed values (`:does_not_exist:`, `:sm`, a lone `:`) stay literal text, so mixed setups degrade to readable shortcodes. Disabling the toggle also shows shortcodes as plain text.

A small smiley button in the strip above the right end of the chat input toggles the emote picker; selecting an emote inserts its shortcode at the current cursor position without disturbing the rest of the input, and the panel stays open for further picks. The picker has a search field that filters by name, a Favorites row (right-click any cell to toggle a favorite, marked with a small gold dot), a Frequently Used row ranked by how often each emote has been sent, and the full grid; hovering a cell shows its shortcode as a tooltip. Favorites and usage counts are per-installation client preferences stored in `config/losttales/chat_emotes.txt` — nothing is synchronized. The button and panels are positioned from the live chat geometry, so GUI scale and resolution changes are handled.

Typing an unclosed shortcode such as `:fl` shows a completion list above the input, filtered live as more characters are typed. Click a row or use Up/Down plus Tab or Enter to complete it (Enter never sends the message while the list is open); Escape hides the list without closing chat. Completions never anchor on the closing colon of an already-completed emote, and commands never trigger the list.

The canonical registry is the `ChatEmoji` enum (`chat/emoji/`), which doubles as the picker order. Adding an emote means drawing it into a free 10×10 cell of `textures/gui/emotes.png` (11-pixel stride, 1-pixel gutters) and adding one enum constant naming that cell; `ChatEmojiSheetTest` fails the build if the sheet and registry disagree. Shortcodes are lowercase `a–z`, `0–9`, `_` and are wire format: never rename or reuse one. `ChatEmoji` and the parser are deliberately free of client classes; sprites, markers, the picker, and rendering live in client-only code.

Every chat element shares one shadow rule: text, emotes, head icons, item icons and marker glyphs draw a flat `#2d1e2f` silhouette at half the content's opacity, offset one pixel down-right under it. Sprites get that through `LostTalesSilhouetteRenderState`, which swaps the texture environment so a textured quad takes its colour from one constant and only its alpha from the texture; a tinted copy of the sprite would keep its own dark outline and go black instead.

Inline glyphs — emotes, item icons, map-marker glyphs, and the quest glyph on the toolbar — follow one set of rules in `ChatInlineIcons`, in the message lines, the pickers, the completion lists and the toolbar buttons alike: a glyph occupies the ten-pixel slot its two bold spaces reserve and fills a ten-pixel content box centred in it, two rows above the text's top edge so it is centred in the eleven-pixel band. An emote is drawn 1:1, an item's sixteen-pixel sprite is scaled onto the box, and a marker's opaque artwork (using the art bounds the marker atlas already records, not its padded seventeen-pixel cell) is fitted into it by its larger edge — always uniformly, never stretched — so every kind reads at the same apparent size with the same baseline, spacing and shadow. A marker glyph and the bracketed name beside it keep the colour the marker has on the map, except that the map's plain white becomes the chat's ivory so a white marker and the text around it share one white. On the toolbar buttons every glyph fills the same ten-pixel box centred in the twelve-pixel button, fitted by its larger edge exactly as it is inline — the emote 1:1, the sword's sprite scaled onto the box, the point-of-interest and quest marker glyphs fitted uniformly — so the emote, item, marker and quest buttons read at one size on one baseline with one hitbox, and nothing is stretched.

## Sharing items and locations

A player can share an item from their own inventory or a map marker inline. The strip above the input's right end runs, right to left: the emote button, the sword button, which opens an item picker (search field plus collapsible Hotbar, Inventory and Armour sections), the marker button, which opens a picker of every map marker the map would show, and the quest button. Only places the player has actually reached are offered: a marker must be discovered (if it is discoverable) and its fast-travel region unlocked, and the server applies the same rule on send, so an undiscovered question mark cannot be shared. The marker picker opens with a **Favourites** section (right-click a row to toggle, marked with the same gold dot as the emote picker) and a **Recently Travelled To** section (the last eight destinations the player actually arrived at, most recent first — reported by the server from LOTR's own fast-travel completion through `LostTalesFastTravelArrivalPacket`, so a refused or cancelled travel never counts), followed by one collapsible section per marker type — the glyph the marker is drawn with, which is the taxonomy the marker atlas already defines: Settlements, Graveyards, Forests, Mountains, Ports, Harbours, Bridges, Camps, Waypoints, Points of Interest, Quests and so on — instead of one generic "Point of Interest" list. Sections with nothing in them are not shown — in every picker, so an empty hotbar or inventory section simply does not appear — and a search shows one flat result list. No picker grows past the middle of the screen: a longer list scrolls inside the panel with the mouse wheel, clipped below the search row, with a thin track at the right edge. Favourites and recent destinations are per-installation client preferences stored in `config/losttales/map_markers.txt`, keyed by marker id; an id that names no visible marker on the current server is kept but not shown. The quest button opens the quest picker on the same frame; quest entries are not shareable yet, so it shows an empty-state line, and quest entries will slot into that picker without another redesign. Typing `[i:` or `[m:` instead shows a completion list (icons and names; duplicates are numbered `Name (2)`). Either inserts a token such as `[i:Iron Sword]`, `[i:Iron Sword#2]` for the second stack of that name, or `[m:Northgate Test City]`. A shared marker renders as its glyph in the chat's ivory plus its name in the marker colour; hovering shows its coordinates and clicking opens the LOTR map and flies the camera to it (with the selection frame when the marker is known locally). Up to three items fit in one message, and a token counts as a single character against the 100-character limit, which the field itself enforces. When the message is sent, the client resolves each token to a reference — a slot index for an item, a marker id for a marker — and sends only that alongside the text; the server re-reads the slot from the sender's live inventory or the marker record from world data under the sender's own visibility rules, checks that the real name matches the token, and attaches a validated payload (a stack bounded to 1 KiB of compressed NBT, or the marker's public id, name, icon, colour, dimension and coordinates) to the message it distributes. Recipients render a validated token as a small icon plus the bracketed name in its rarity colour, with the item's normal tooltip (name, enchantments, lore, attributes, durability, mod tooltip lines) on hover; the stack is decoded once on arrival. A token the server could not verify — the item was moved or dropped before sending, the name no longer matches, a forged slot, or an over-sized stack — is delivered as the literal text the sender typed, and the sender is told once per message. Showcase tokens, like emotes, are plain message text on the wire and in copied history.
